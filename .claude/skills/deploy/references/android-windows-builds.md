# Staging APKs and the Windows installer

Read when the task needs it; the short rules are in `SKILL.md`.

## The staging APKs

Every merge to `main` but one of docs only runs the `staging-apks` job of `.github/workflows/ci.yml` after `verify`: it builds the customer, restaurant and captain apps with `flutter build apk --flavor staging --release`, pointed at `https://<API_HOST of infra/environments/staging.env>`, and keeps each as an artifact of the run for 30 days (`foxdrop-<app>-staging-<run number>`, Android only; owner decisions 2026-11-07). Download them from the run's page (Actions › CI › the run › Artifacts) or with `gh run download <run id> --repo HussienALfajer/fox-drop`. The staging apps have their own IDs (`com.foxdrop.<app>.staging`), so they install beside development builds (`.dev`); Android asks to allow installs from unknown sources.

Each app has its own staging key (architecture §11.4): the secrets `STAGING_<APP>_KEYSTORE` (the PKCS12 key store in base64) and `STAGING_<APP>_KEYSTORE_PASSWORD` of the GitHub `staging` environment, alias `foxdrop`. The owner keeps a copy outside the repository. A new key cannot update an installed app: uninstall the staging app first. A build of the same flavor on a machine without the key is signed with the debug key; never hand it out.

The captain APK's background location (`flutter_background_geolocation`, architecture §14.1, §22 item 8) needs its Android licence key in the secret `STAGING_CAPTAIN_BGGEO_LICENSE` of the `staging` environment (owner decision 2026-11-20: bought later), generated in Transistorsoft's dashboard for the staging app ID `com.foxdrop.captain.staging` (a key is tied to the app ID; production gets its own with its environment). A wrong key leaves the staging APK without any location: the build cannot tell. Until it is set the staging APK tracks through `geolocator` while the app runs, as before (its points kept in memory); once set, `staging-apks` passes `BACKGROUND_LOCATION_LICENSED=true` and the APK tracks through the library, its points kept across a restart. A debug build always uses the library, which needs no licence there.

## The staging Windows installer (slice 2.44)

Every merge to `main` but one of docs only runs `staging-windows` (on `windows-latest`): `flutter build windows --release` of the restaurant app, pointed at the staging API, with `WINDOWS_UPDATE_FEED=https://<API_HOST>/downloads/windows/`; then Velopack's `vpk pack` (pinned in `ci.yml`) as `FOXDROP.Merchant.Staging`, version `<pubspec version>-staging.<run number>`. The run keeps the files as an artifact for 30 days, and `publish-windows` sends them as a tar through the deploy key (`staging windows`, `deploy-ssh.sh`) to `foxdrop-windows-publish staging` (`infra/server/windows-publish.sh`), which extracts the tar as `nobody`, takes only Velopack's files and the feed's signature, puts the packages first and the feed last in `/var/www/foxdrop-staging-downloads/windows/`, and removes packages the feed no longer names after 14 days. nginx serves that folder as `/downloads/windows/` (reads only). The installer is `https://<API_HOST>/downloads/windows/FOXDROP.Merchant.Staging-win-Setup.exe`; it installs per user, without administrator rights, in `%LocalAppData%\FOXDROP.Merchant.Staging`. The installed app reads `releases.win.json` at its start and every hour and restarts into a newer package only when nothing is open (RA §4.2).

- **The feed's signing key** (separate from the deploy key, so whoever holds that key or the folder cannot make the PCs install a file): the app updates itself only from a `releases.win.json` signed by it. On the owner's computer, once: `openssl genpkey -algorithm ed25519 -out feed.pem`, then `openssl pkey -in feed.pem -pubout -outform DER | tail -c 32 | base64` gives the public key. In GitHub, environment `staging`: the secret `STAGING_WINDOWS_FEED_KEY` is the whole of `feed.pem`, the variable `STAGING_WINDOWS_FEED_PUBLIC_KEY` the public key; keep `feed.pem` in the password manager and delete the file. Until both are set, the build warns, carries no key and never updates itself (install each new build by hand). A new key needs a new install, since the public key is built into the app.
- **First time:** provision from the commit on `main` that has this (`provision.sh` installs the script, its sudo rule, the folder and the nginx location); before that, `publish-windows` fails with the key's usage message.
- **Unsigned** (owner decision 2026-11-20): SmartScreen shows «Windows protected your PC»; «More info» › «Run anyway». Azure Trusted Signing comes later (architecture §22 item 8): its account, certificate profile and the CI secrets, then a signing step in `staging-windows` (`vpk pack --signTemplate` or `--azureTrustedSignFile`).
- **A Windows PC registers once** with an owner's pairing code (the restaurant app on Android: «الإعدادات» › «الأجهزة» › «ربط كمبيوتر بويندوز»). While `otp.app_check_required` is off it signs in unpaired; once it is on, its first refused code request opens «ربط هذا الكمبيوتر», and its code requests pass with that registration's signature.
