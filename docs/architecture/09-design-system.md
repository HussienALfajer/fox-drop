# 9. Design system (T2, T10, T11, T14)

> Part of the [technology stack](README.md). A bare "§n" here means §n of the technology stack. Method and rules decided by the owner on 2026-11-21 (T10); headless bases in T11. The slices that build it are Phase D in `docs/roadmap.md`.

## 9.1 Method: code is the source, design comes first

- **Code is the source of truth.** Tokens and components are edited in code. The Claude design project (§9.8) mirrors them and is never edited by hand.
- **Design before code, with the owner's approval as the gate.** A screen is drawn in the design project and approved by the owner before it is coded; a component batch is approved as its built web components' cards (T14, below). The design is not bound by the feature specs; the specs decide behaviour, the owner decides the look.
- **Web first (T14, owner 2026-11-26).** A component's drawing is its web component: built in `packages/ui-web`, it is shown live in the Design System (§9.8) and the owner approves that card. A Flutter twin has no drawing of its own: its drawing is its parity sheet (`pnpm parity`: each web story beside its Flutter case, same tokens, same states), and its goldens are the check.
- **What a drawing does not decide.** Keyboard behaviour in RTL, focus, typeahead, screen-reader output and digit entry are proven by tests only. A parity sheet is a visual reference, not a pixel contract: golden tests are the Flutter check.
- **Direction of flow:**

```
packages/design-tokens ──generate──▶ web theme · Dart theme · design-project tokens
packages/ui-web (tested) ──sync──▶ Fox Drop Design System (live web components)
ui-web component ──parity sheet──▶ core_ui twin        approved screen ──▶ screen code
```

- A token changes in `packages/design-tokens`, is regenerated and synced. A web component enters the design project only after it is built and tested; a Flutter widget never does.

## 9.2 Token layers

Tokens are W3C Design Tokens (JSON) in `packages/design-tokens`, compiled by **Style Dictionary** into CSS variables and a Tailwind theme (web) and pure-Dart constants in `packages/core_tokens`, which `core_ui` wraps (Flutter). A change reaches both platforms in the same build.

| Layer         | Holds                                                                                                                                                                             | Used by                                    |
| ------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------ |
| **Primitive** | Raw values: the brand colours (ivory `#FFFAED`, orange `#FF6E31`, blue `#03428E`), their scales, the Figma ground `#FBF2E7`, spacing steps, radii, shadows, durations, type sizes | Semantic tokens only                       |
| **Semantic**  | Meanings: surface, on-surface, primary, accent, border, success, warning, danger, focus ring, and so on. Each has a light value and a **dark slot**                               | Components and screens; the Tailwind theme |
| **Component** | Per component: its height, padding, radius, colour roles per state                                                                                                                | That component only                        |

- **The colours of the Figma file (D.3, owner 2026-11-23).** The ground is `#FBF2E7`, raised cards `#FEFEFE`. Text, prices and numbers are blue `#03428E` by default (8.72:1 on the ground), and so are headings (`heading`, bold), as the identity package V1.1 sets them (owner, 2026-11-25). The brand orange **`#FF6E31`** carries buttons, bars and the logo in every app, the captain's included, although it misses 4.5:1 (2.52:1 on the ground, 2.68:1 under ivory text): the owner's exception to R4. D.8 (owner, 2026-11-23) extended it to `primary` as a 3:1 non-text element on `surface` and `surface-raised` (2.52:1 and 2.77:1): a focused field's outline, checked controls, the switch, the stepper and the orange icons inside controls. Then the owner allowed orange anywhere (2026-11-23), text, links, prices, amounts, timers and small labels included, under the same exception: no use of the brand orange is a bug; each orange pair a design uses is listed in `src/contrast.ts` so the report shows its ratio. The accessible orange `#C2410C` of D.2 is retired as a text colour; it remains the pressed step `primary-pressed`. Every pair and its ratio: `packages/design-tokens/generated/contrast-report.md`.
- **The component layer declares its readers (slice D.W1).** Each file of `tokens/component/` is one component and comes out, with no change to the generator, as `--fd-<component>-*` variables and as a Dart class bundled per theme in `ComponentTokens` (`FoxThemeData.components` in `core_ui`). The file names the `ui-web` and `core_ui` folders that read it in `$extensions["app.foxdrop"]` (`{ "web": [...], "flutter": [...] }`), and a test fails when one of its tokens is not read on a declared side; a token only one side needs says `"sides": ["web"]`. A component's file arrives in the slice that moves both its sides onto it.
- **Dark mode comes later.** Every semantic token has its dark slot from D.2 so no component has to change when dark mode is built; V1 ships light only.
- **Foundations:** a 4-point spacing grid; a functional type scale; radius, elevation and motion tokens (reduced motion is respected); two densities, comfortable for the phone apps and compact for the panel; web breakpoints; phone safe areas.
- **Governance:** tokens are versioned with a changelog; a token is deprecated for a release before it is removed.

## 9.3 Typography

- **CoFo Sans Pro Arabic** is the UI typeface (text, headings, buttons). **YR-Speed** is for display and promotional use outside the apps. **Emad-Diana** is not used in the UI (owner, 2026-11-23; brand expression §7), although the Figma file sets its button label in it. The brand guidelines name HTQaysSansPro, which is not in the pack. Neither CoFo nor Emad-Diana has the ₺ glyph (U+20BA): D.6 and D.7 must give the money component a fallback for it.
- The fonts are licensed, not open: CoFo is "All rights reserved" (embedding flag `fsType` 4). **The font files stay outside this public repository** (they live in the private repository `HussienALfajer/fox-drop-fonts`; `docs/brand/fonts-manifest.json` pins its commit and every file's SHA-256, and `pnpm fonts:fetch` puts them in the ignored `.fonts/` before the apps and web bundles are built; a test refuses a font file in any commit of a pull request, by extension or by signature); the repository holds only their names, weights and metrics. Fonts are bundled in the apps and self-hosted on the web, never loaded from a third-party font CDN.
- **Western digits everywhere** (AP §4.7), with tabular figures for money, timers and tables.

## 9.4 Icons

- FOX DROP's own icon set, **v4 "Madar"** (owner, 2026-11-24; it replaced the D.5 set): drawn from scratch on the construction measured from Solar, one source for web and Flutter. One SVG per icon in `packages/design-tokens/icons/`, with the manifest `icons.json`.
- **The construction:** the 24 grid; every point inside the live area 2..22 (the test's rule), bodies drawn to sit inside 2.25..21.75 where the shape allows (the clasp of `wallet` and the pin of `route` reach 22); stroke 1.5 with round caps and joins, 1.75 in the captain theme (`icon-stroke.phone`, `icon-stroke.captain`). At most 2 decimals. Sizes `size.icon-sm` 16, `size.icon-md` 24, `size.icon-lg` 32; the stroke scales with the size.
- **The continuous corner:** each corner is two cubics, with handles at 0.5286 s and 0.2929 s of the corner's extent s and the diagonal point at 0.1464 s, generalised to any angle. Dots are zero-length paths.
- **One body, one meaning:** each icon has one body and one meaning detail. A detail floating inside or beside the body keeps about 1.5 clear of it; a detail that joins the body (a clock's hands, a door) meets it, and Bold knocks it in or draws it out by its role. Eight bare glyphs have no body: `back`, `close`, `chevron-down`, `menu`, `add`, `remove`, `confirm`, `retry`.
- **Element roles**, one `<path d>` each, as data attributes: `data-role` `body` or `detail`; a detail's `data-knock`, `in` (knocked out of the body in Bold) or `out` (drawn as a solid line); and the flags `data-accent` (the meaning layer), `data-fill` (filled in Bold), `data-open` (an open body, never filled) and `data-halo` (crosses the body).
- **Six styles from one drawing,** and where each is used:
  - **Linear,** the default: every element stroked.
  - **Bold:** the bodies filled, `in` details knocked out at the stroke width, `out` details drawn solid. A chosen favourite's heart, the captain's large buttons. The selected bottom tab stays Linear: its larger orange circle alone marks it (owner, 2026-11-25, D.11b).
  - **Brand Duo:** Linear with the accent stroked in `brand`. Empty states, promo cards, settings chips.
  - **Bold Duo:** Bold with the non-accent bodies at 0.5. Coloured cards and important notices.
  - **Duotone:** Linear with the non-accent elements at 0.5. **Broken:** Linear with the bite. Marketing and illustration.
- **The bite** (Broken): one 2.25 gap in the primary body (its first non-accent body, else its first), centred on its point nearest (22, 2). On an open body the bite slides along the line to the nearest point where a whole gap fits with a stub of at least 1.5 at each end (owner, 2026-11-24).
- **The halo** (Bold): a 1.25 gap is cleared around an element that crosses the body.
- **Baked, not masked:** Flutter's Canvas has no SVG masks or dash offsets, so Broken, Bold and Bold Duo are computed once at generate time with CanvasKit (Skia, the engine Flutter draws with) into plain path data, Bold and Bold Duo at both strokes (`src/icon-bake.ts`).
- **Mirroring:** sources are drawn left to right; exactly `back`, `motorcycle` and `car` flip in RTL.
- The set is exposed through an `Icon` component on each platform (D.6, D.7), so the set can change without touching screens.

## 9.6 Web components: `packages/ui-web`

- The headless base is **UI SDK** (`@ui-sdk/react`), with **Base UI** as the per-component fallback (T11, §9.10). They handle focus, keyboard navigation, ARIA and RTL behaviour; FOX DROP supplies every look.
- `packages/ui-web` builds FOX DROP's own components on them: buttons, inputs, tables, cards, badges, alert banners, timers, money and status chips, the order card, and so on. Styling is Tailwind CSS on the semantic tokens, with logical properties (`ms-*`, `pe-*`, `start`, `end`) so RTL is the default and LTR works later (AP §12 lists English for V2). Variants use `tailwind-variants`.
- **Storybook** documents every component in RTL with all its states, with visual tests (§18).

## 9.7 Flutter components: `core_ui`

- `core_ui` implements the same components as Flutter widgets on the Dart theme. A twin is built when a screen of a Flutter app needs it (T14), after its web component: on the same component tokens (`tokens/component/`, a token one side does not draw marked `sides: ["web"]` or `["flutter"]`), with a parity case for each of the web story's states that it draws, and checked on the parity sheet before its goldens are taken. The apps use only `core_ui` widgets, never Material or Cupertino widgets (R2), so they look like FOX DROP.
- The behaviour base is chosen per component behind the `core_ui` API, with no third-party UI package (T11, §9.10; owner, 2026-11-23): simple components (button, icon, chips, cards, list rows, badges) on Flutter's widgets layer; complex ones (text input with its selection controls, date and time pickers, dialogs, bottom sheets, pull to refresh) may wrap `material_ui` inside `core_ui`, themed wholly from the tokens with ripples and Material defaults off. Apps never import Material or Cupertino (R2).
- RTL by default (`Directionality` from the Arabic locale). Layouts stay usable with the system font at 130% (RA §4.8, CA §4.7, CU §4.6).
- A widget catalogue app (**widgetbook**) documents the components with all their states, like Storybook on the web.

## 9.9 The cycles

- **Component cycle (per batch, T14):** (1) the batch's web components are built in `ui-web` with every state (default, hover, focus, pressed, disabled, invalid, loading), both densities, RTL, on component tokens, with their stories and tests; (2) they are synced and their boards on "Fox Drop Components" are generated from the bundle (`pnpm --filter @fox-drop/ui-web components-canvas`, T15); each board is the drawing the owner approves once per batch. A component whose look must be settled before any code is drawn first on the canvas's proposals page with the owner, then coded, its drawing deleted and its board generated; (3) a Flutter twin, when a screen needs it, is its own slice: its checkpoint is its parity sheet, each gap fixed on the side the approved card or sheet says, never a second drawing.
- **Screen cycle (T13, owner 2026-11-24):** an app's screens are built in **UI batches**, one slice each, after the API the batch uses is built. A batch groups screens of one flow (for the customer app: sign-in and account, location and addresses, finding food, restaurant page and cart, checkout, the active order, after the order and my account).
  1. **Inventory.** The slice file lists each screen of the batch with the spec section it cites (the spec is not rewritten): its purpose, sizes, the five states of R6 and every state the spec names (closed restaurant, outside the zone, maintenance, forced update…), and the data and actions of each. What the spec does not settle goes to `docs/open-questions.md` and the owner; it is never guessed.
  2. **Draw.** The batch's first checkpoint draws its screens on the app's screens canvas with the Fox Drop Design System installed: its real components (screens are drawn with the live web components, which stand in for their `core_ui` twins; the parity sheets and goldens remain the Flutter check, §9.1), its tokens for every colour, space, radius, shadow and size, its type styles; no literal value and no look-alike. Arabic RTL, the sizes needed, synthetic data. Before they are shown, the artboards are checked for literal colours, unknown token names and hand-drawn copies of components, and the result is written in the slice file. Drawings made before their batch (the Figma file's screens included) are drafts, not approvals.
  3. **Prototype.** Every artboard is interactive: fields take typing, buttons act, the flow runs from screen to screen, and every state of the inventory is reachable by the action that causes it or by a labelled state switcher outside the frame. Nothing calls a real API.
  4. **Analysis**, in the slice file and shown with the drawings: (a) a table of every route the batch uses, every response field and every error code, each shown on a screen, driving a state, or named with the reason it is not shown; (b) API gaps and unprofessional answers (an error the client cannot tell apart, a list without the order the screen needs, raw ids), fixed in the server in the batch or a small slice before it, never worked around in the app; (c) spec gaps, sent to the owner; (d) improvements for Azaz (fewer taps, smart defaults, slow-network and offline cues, clear Arabic), each with its cost, accepted or declined by the owner; (e) missing components.
  5. **Missing component:** drawn in the same checkpoint on its own sheet with all its states and at once on every screen that needs it; the owner approves it with the screens. It is then built in `ui-web` with its tests and synced before the screens use it (its `core_ui` twin, for a Flutter app's screens, checked on its parity sheet), in the batch's pull request or its own one before it. Never a one-off in a screen.
  6. **Designer pass:** the approved-candidate screens go to Figma for the designer; the edits are read back into the prototype. A new value the designer introduces becomes a token change in code, or is declined.
  7. **Approval:** the owner tests the batch in Play and approves it. Nothing in the batch is coded before.
  8. **Code and evidence:** coded to match, against the local server; each screen has a golden on an Arabic phone at 360 × 640 and a medium size and at 130% text, and the app's own screenshot is compared with the drawing, each difference fixed or explained in the slice file. The customer app is light only in V1 (CU §17).
- **Later changes:** a colour, type or component change starts in code and is synced; a screen change starts in its drawing, then its code.

## 9.12 Brand expression (D.1b)

Sections §9.1 to §9.10 govern the system; this one gives it its character. Every item below was decided by the owner on 2026-11-22 (slice D.1b) and is written in [`docs/brand/expression.md`](../brand/expression.md), which D.2 and D.3 use.

| Item                       | Decides                                                                                                                                                       | Feeds      |
| -------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------- |
| Principles and personality | Three to five design principles and the brand's personality, the yardstick every design decision and every D.3 direction is judged against                    | D.3 on     |
| Signature shape            | Whether the logo's drop becomes a shape language (cards, badges, the map pin, loading), and where it stops                                                    | D.2, D.3   |
| Motion language            | What motion means for FOX DROP: the order-confirmed moment, the courier moving on the map, transitions, haptics; the reduced-motion fallback                  | D.2, D.6/7 |
| Map style                  | Base map colours, restaurant, customer and captain pins, the route line, the captain's sunlight view                                                          | D.3        |
| Illustration and photos    | The illustration style for empty, error and offline states and missing photos; a food-photo guide for restaurants                                             | D.3, R6/R7 |
| Full palette               | Tonal scales of the three brand colours, status colours that fit them, a chart palette for the panel, and whether the captain app targets 7:1 for sunlight    | D.2        |
| Arabic typography          | The Arabic type scale and line heights, the Latin companion of CoFo, mixed-script alignment, a check that CoFo has tabular Western digits, how many typefaces | D.2        |
| Voice and tone             | Modern Standard Arabic or Syrian dialect, per surface; the tone of errors, waits and apologies                                                                | R5         |
| Device budgets             | Font subsetting and size limits, image weights, behaviour on low-end Android phones and weak networks                                                         | D.2, D.6/7 |
| First icon set             | The size of the first hand-drawn set (about 40 core icons) and what waits                                                                                     | D.5        |
