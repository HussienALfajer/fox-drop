# apps/customer

The customer app «تطبيق الزبون» (Android, iOS), a Flutter app in the Dart pub workspace (architecture §11, §13). `apps/captain` (Android, iOS) and `apps/merchant` (Android, Windows) follow the same rules.

## Layout

- `lib/main.dart`: starts App Check (`startAppCheck`, `packages/core_auth/CLAUDE.md`) and push (`startPush`, `packages/core_push/CLAUDE.md`), then runs the app inside a Riverpod `ProviderScope` that gives the scope its token source.
- `lib/src/app.dart`: `MaterialApp.router`, fixed to Arabic. `lib/src/router.dart`: the go_router routes, as a provider.
- `lib/src/api.dart`: the API client providers and the server address. `lib/src/auth.dart`: the app's `AuthScope` (`packages/core_auth/CLAUDE.md`). `lib/src/device.dart` (customer): the device store, the clock and the app version. One screen per file next to them, until a feature needs a folder.
- Feature folders (customer, slice 1.14d): `profile/`, `location/`, `browsing/`, `cart/`, `checkout/`, `orders/`, and `notifications/` (slice 2.3b). Each keeps its logic (providers, notifiers, pure functions such as `ItemChoice` or `problemViews`) in plain files and each screen in a `*_screen.dart` or `*_sheet.dart` that only reads that state and calls it (the design stop).
- `test/`: widget tests, run by `flutter test`.
- `android/`, `ios/`, `windows/`: written by `flutter create` with the app ID `com.foxdrop.<app>` (owner decision 2026-11-05). Edit them only for a reason, and say it in a comment.

## Rules

- **Libraries (architecture §11.3):** Riverpod for state and dependency injection, go_router for navigation; no other state library, no `Navigator.push` for screens. Every dependency is pinned to an exact version; a package shared with another member of the workspace takes the same version.
- **API (E6):** call the server only through `coreApiProvider` (the generated `core_api` client, with the session's interceptor) inside a provider; never Dio or `http` by hand. `authApiProvider`, without the interceptor, serves only the app's `AuthParty`. Tests replace both with `FakeServer` clients (`package:core_auth/testing.dart`) and the scope's `store` with `MemorySecureStore`, so they need no server or device.
- **Session and routes (slice 1.14b):** the router redirects on the scope's session: `/starting` while it is read, `/sign-in` when signed out (the customer app lets guests stay, CU §5.1), home once signed in. In the customer app a screen that needs sign-in sends the guest to `signInFrom(<its path>)`, and sign-in returns to that `from` (only a path of the app); while `GET /v1/customer/profile` answers `completed: false` every route goes to `/complete-profile` («أكمل بياناتك», CU §5.3) with the same `from` (slice 1.14d). The restaurant app sends a signed-in device without a name to `/device-name` (RA §5.2 item 5); the captain's sign-in screen shows «سُجّل دخولك من جهاز آخر» after `other_device` (CA §4.9).
- **Ordering (customer, slice 1.14d; CU §7, §10):** the delivery point (`deliveryPointProvider`) comes from the phone through `positionSourceProvider` (`geolocator`; tests use a fake) or a saved address's pin, and lives while the app runs; the last request wins, and the checkout's chosen address is the point's `addressId` (null for the point as an unsaved address). Sign-in from checkout and «أكمل بياناتك» use `context.go`, so the router's redirect sees them; «تأكيد الطلب» reads the profile first and never sends without a completed one. The cart is the only state kept on the device (`DeviceStore`, 24 hours), with each line's `unitPrice` as the quote's `knownUnitPrice`; «موافق» on a new price updates it; a problem's action finds its line by `CartLine.key`, never by index. `quoteProvider` re-asks on every change of the cart, the point or «سأدفع بـ», and every problem it lists blocks «تأكيد الطلب» (`problemViews` maps them to CU Appendix C). `placeOrderProvider` is kept alive, so leaving checkout never cancels a command, and `CustomerApp` opens the placed order wherever the customer is; its `Idempotency-Key` belongs to one command body (a lost answer resends the same key, a refusal or another body takes a new one). The far-pin check (`farPinMetres`) runs on the device only and never asks for the permission. Amounts are minor-unit strings formatted with `formatMoney`, and the money models the generator shares come out nullable in Dart (`price!`), though the server always sends them.
- **The live order (customer, slice 1.14e; CU §4.3, §6, §11):** `orderFeedProvider(id)` is a `LiveFeed` (`packages/core_realtime/CLAUDE.md`) of `GET /v1/customer/orders/{orderId}` over `order:{order_id}`, opened with the order screen and closed with it; the screen never patches the order. `titleOf` maps the order to the title and subtitle of CU §11.2 and §11.9 (the captain from `captain`, never the captain track), `stepOf` to the five-step progress; `titleTexts` and `statusText` turn them into strings. The home's active-order bar (`activeOrdersProvider`, CU §6) is read when home opens. Every countdown runs on `serverClockProvider` (`packages/core_time/CLAUDE.md`). Tests drive the channel with `FakeTransport` (`test/fakes.dart`, in `TestApp`) and end a test that opens an order with `app.done(tester)`, which stops the feed's polling before Flutter checks for pending timers. Not yet: the map and «اتصال بالكابتن» from pickup (CU §11.3), «مساعدة» and «إلغاء الطلب» (§11.4–11.5), the banners (§11.6), the door ping (§11.7), the rating sheet and the delivery's amounts (§11.8), the reasons and similar restaurants of §11.9, and the bar's refresh while home stays open.
- **Push (customer, slice 2.3b; CU §4.4, §13, §14):** `pushTokensProvider` keeps the installation's token registered while signed in (`PUT /v1/customer/push-token`) and `pushTapsProvider` opens a tapped push's target, both watched by `CustomerApp`; `pushTargetPath` maps a push's data to a route (only `order` today; «أكوادي» and the account with their slices), for the «الإشعارات» screen too. Android's channels `default` and `ring` are created in `MainActivity`. The permission is asked once per installation (`notifications_asked` in the device store), at the first order, after the far-pin check and before the command: «سماح» asks the phone, «ليس الآن» does not, and the order goes either way (`NotificationAsk`); a phone that already allows notifications is not asked. While the customer was asked and the phone does not allow them, an active order's screen shows `NotificationsOffBanner`, which opens the phone's settings and is read again when the app resumes. «الإشعارات» (`/notifications`, signed in only) reads `GET /v1/customer/notifications` when it opens; it is reached from home until «حسابي» exists. Tests give `FakePush` through `pushProvider`, and `TestApp.permission`, a `FakeNotificationPermission` that allows notifications unless the test says otherwise. Not yet: a push received while the app is in the foreground is not shown (the screens are live), the app's own sounds for «الكابتن عند الباب», iOS.
- **Content (slice 2.1; AP §9.13):** each app reads `GET /v1/<app>/content` once into its `contentProvider` (`lib/src/content.dart`, kept for the app's life; a failed read is read again with `ref.invalidate`): the reason lists it picks from, as `{ code, label, needsText }`, and its FAQ set. A reason list is never a constant in an app: the choice sends the code back, shows the label, and offers a text field when `note` is `optional` or `required` (required: «أخرى»). A command refused with `unknown_reason`, `reason_note_required` or `reason_note_not_allowed` means the panel changed the list: the app reads it again (`ReasonChanged` in the captain app) and the person chooses again. The customer app shows «الملاحظات الجاهزة» at checkout (none while not read), the FAQ at `/faq`, and the `cancellation.text` of an order operations cancelled under «أُلغي طلبك» (the automatic cancellation keeps CU §11.9's own «لم يرد المطعم على طلبك، نعتذر»); the captain app takes the away and shortfall reasons from it and shows the work rules (`/work-rules`, one rule per line) and the FAQ (`/faq`).
- **Server address:** `--dart-define=API_BASE_URL=http://<address>:3000`. Without it a debug build uses the development machine (owner decision 2026-11-05): `10.0.2.2:3000` on the Android emulator, `localhost:3000` on iOS Simulator and Windows; a phone needs the machine's address. A release build refuses to start without it: `main()` reads the address before `runApp`. Android has three flavors (architecture §11.4, slice 1.14b): `development` (`.dev`, the pubspec's `default-flavor`, so `flutter run` needs no flag), `staging` (`.staging`) and `production`; CI builds the staging APKs signed with each app's key (the `deploy` skill, «The staging APKs»). A release build without `FOXDROP_KEYSTORE_FILE` is signed with the debug key: never hand it out. iOS has no flavor schemes yet (Android only for now, owner decision 2026-11-07), so `flutter run` on iOS fails on the default flavor until the iOS slice adds the matching Xcode schemes. On Windows, when the repository and the pub cache are on different drives, a release build needs `--android-project-arg=kotlin.incremental=false` (Kotlin's incremental caches fail across drives). Plain HTTP is allowed only in the Android debug manifest and, on iOS, for the local network (`NSAllowsLocalNetworking`). Firebase (App Check) takes four more `--dart-define` values, which CI passes to the staging APKs (the `deploy` skill, «App Check»); without them the app sends no App Check token, which the local server accepts while `otp.app_check_required` is off. Never put a key or secret in the app (E7): every `--dart-define` ships inside it, the Firebase API key included, which is an identifier, not a secret.
- **Arabic, right to left (AP §4.7):** every user-facing string is a getter of `AppLocalizations` from `core_l10n` (`packages/core_l10n/CLAUDE.md`); never a string literal in a widget. The app's `locale` is `ar`, so Flutter lays it out right to left. Use `EdgeInsetsDirectional`, `AlignmentDirectional` and `start`/`end`, never `left`/`right`. The launcher name and the system's permission texts are the only text outside ARB: `android:label` in `AndroidManifest.xml`, the push channels' names in `res/values/strings.xml`, `CFBundleDisplayName` and the `NS…UsageDescription` keys in `Info.plist`, and the window title in `windows/runner/main.cpp`.
- **Design stop:** no `core_ui`, theme, colours, fonts or styling until the owner says the UI/UX and the design system are ready (root `CLAUDE.md`). Screens use plain Material widgets with their defaults.

## Commands

From the app's folder, with the pinned Flutter (`.fvm/flutter_sdk/bin` first on `PATH`), after `docker compose up --detach` and the server on port 3000:

- `flutter run`: on the running emulator, simulator or (merchant) `-d windows`.
- `flutter test` and `dart analyze --fatal-infos`: what `pnpm verify` runs for every Flutter package through Melos.
