# apps/merchant

The restaurant app «تطبيق المطعم» (Android, Windows; architecture §11, §12). It follows the rules of `apps/customer/CLAUDE.md`.

## The board (slice 1.14e; RA §4.3–4.7, §8.1–8.11)

- **Layout:** `lib/src/board/`. `board.dart` holds the rules as pure functions (columns, sorting, lateness, the captain line, what rings) and the feed; `commands.dart` the commands; `alerts.dart` the ring and the chimes; `texts.dart` every string mapping; the `*_screen.dart`, `prompts.dart` and `dispute_sheet.dart` files only show that state and call it (the design stop).
- **State:** `boardFeedProvider` is a `LiveFeed` (`packages/core_realtime/CLAUDE.md`) of `GET /v1/merchant/orders` over `merchant:{restaurant_id}`; the screens read `boardProvider` and never patch it. The order detail (`/orders/:id`) reads the same board, so it never shows another version of an order.
- **Time:** every countdown and «منذ» runs on `serverClockProvider` (`packages/core_time/CLAUDE.md`), through `tickProvider` once a second; never `DateTime.now()`.
- **Commands** (`BoardCommands`, RA §4.7): one at a time per order, shown as «جارٍ الإرسال…»; the `Idempotency-Key` belongs to the command and its body, and a call without an answer (no response or a 5xx) is sent again with the same key after a backoff with jitter until the server answers. Any answer refreshes the board. A `409 order_state_changed` is explained from the order it carries (`commandText`). Commands live in memory: the queue that survives a restart (`core_commands`, architecture §11.2) comes later.
- **Ring and chimes** (RA §4.4; owner decisions 2026-11-07): what rings is derived from the board, never from an event: every `placed` order and every open pickup request, oldest first, one sound for all, the prompts stacked. So the ring stops on every device once any device (or the server) handles it. `alertStep` is the pure rule for the chimes and their notices (automatic cancellation from the event's reason, the prep late at its time and every 5 minutes, the captain's arrival and waiting, a prompt closed by another device, 30 seconds offline). `PhoneRinger` plays the phone's alarm sound looping on the alarm stream and its notification sound, through `flutter_ringtone_player`, until the design's bundled sounds; Windows plays nothing yet. The app rings only while it runs, with the screen kept on while the board shows (`wakelock_plus`); the foreground service, full-screen intents and the Windows tray (`core_alerts`, architecture §12.2–12.3) come later.
- **Tests:** `board_test.dart` proves the pure rules; `board_screen_test.dart` drives the screens with `FakeServer`, `FakeTransport` and `FakeRinger` (`test/board_fixtures.dart`, the board's JSON as the server sends it). Widget tests end with `done(tester)`, which disposes the container inside the test so the board's timers stop before Flutter checks for pending timers.
