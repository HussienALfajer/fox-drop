# identity module

Users of the four products, their sign-in and sessions (architecture §4.2). So far: the admin panel's accounts, first sign-in, sign-in, sessions, roles and permissions, the guard on every route and the admin team (AP §5.1–5.3, §6, §9.15; architecture §10.3, §15.2); the apps' phone sign-in with a WhatsApp code, tokens and sessions, served to the customer, restaurant and captain apps (architecture §8.3.1–8.3.2, §15.1; CU §5.2, §5.4; RA §5.1–5.3; CA §4.9), with the restaurants' owners, cashiers and devices and the captains' sign-in accounts.

## Rules

- **Sign-in name** (owner decision 2026-11-05): an admin account has an email, a phone or both, and signs in with either. Emails are stored in lower case; phones are taken in international form only (`+` or `00`), so no country is guessed (`sign-in-name.ts`).
- **Nothing secret in clear** (architecture §10.3, §15.3): passwords are Argon2id; phones and TOTP secrets are AES-256-GCM encrypted with `IdentitySecrets` (`secrets.ts`), phones with a keyed hash to find them by; backup codes are stored as a keyed hash; setup and session tokens as SHA-256. The keys derive from `IDENTITY_ENCRYPTION_KEY` (32 bytes in base64). `identity.test.ts` reads the stored rows and the audit events and fails on any secret in clear.
- **Other modules' phones:** a module that keeps a phone number, such as a customer address's contact number, encrypts it with `PhoneCipher` (exported), the same key as identity's own phones. The `phone` and `deviceId` request schemas are exported for their routes.
- **Shown once:** the setup token only in the link the command prints, each TOTP secret only in the enrolment that made it (a new call makes a new secret), the backup codes only in the setup's answer, the session token only in the cookie. Tokens and codes travel in bodies, the cookie or a URL fragment, never in a path.
- **First OWN** by the server command only (AP §5.3): `pnpm --filter @fox-drop/server admin:create-owner --email <email>` locally, `node dist/modules/identity/create-owner-command.js --email <email> --phone <phone>` (either or both) in a deploy. It prints the link with `ADMIN_PANEL_URL`, to stdout, never to the logger. Run again with the same name while that owner is still pending, it expires the open links and prints a new one (`admin_account.setup_link_reissue`), so a lost or expired link never locks the platform out; any other case refuses.
- **Roles and permissions are rows** (AP §6.1): `admin_roles`, `admin_permissions` and `admin_role_permissions`, which the application role can only read, so only a migration changes them. `permissions.ts` lists the codes for the type of `@RequirePermission`, and `admin-team.test.ts` keeps the rows equal to AP §6.2–6.3. An account's roles are `admin_account_roles` rows, revoked and never deleted; its permissions are the union of its roles', read at every request, so a role change applies at once. `admin_accounts.roles` is deprecated: migration 0004 copied it into rows and emptied it, and a later migration drops it. `AdminRole` in the settings catalogue must stay equal to `admin_roles` (the same test). Owner decision 2026-11-05, approving three readings AP §6.2 leaves open: OPS holds `restaurants.create`; FIN holds `restaurants.statements` and `captains.money` without `restaurants.read` or `captains.read`; DATA has no `restaurants.read`.
- **Route access:** `RouteAccessGuard` checks every route (`@Public()`, `@SignedIn()`, `@RequirePermission()`, all in `src/http/access.ts`) and puts the session on the request for `@CurrentAdminSession()`. No session answers `401`, a missing permission or a route that declares nothing `403`.
- **Admin team** (AP §5.2–5.3, §9.15), OWN's `admin_team.manage`: create (a pending account and its setup link), change roles, a new setup link for a pending user (owner decision 2026-11-05, so a lost or expired link never strands an account), disable (sessions and open links end at once) and enable, force sign-out, reset TOTP. Links are returned as a token the panel puts in its setup link, after `/setup#token=`. Owner decision 2026-11-05: an action that would leave no active OWN is refused (`last_owner`), and nobody disables themselves (`own_account`); every team action takes the `identity.owners` advisory lock, then checks again that the actor is active and holds `admin_team.manage` (`actor_not_allowed`, `403`).
- **TOTP reset** (owner decision 2026-11-05): the TOTP, the unused backup codes and every session end at once, and the account becomes `totp_reset`. A `totp_reset` link enrols TOTP again with the password the account already has; a wrong password counts towards the lockout (`lockout.ts`). The enrolment issues 10 new backup codes.
- **Setup link:** valid 24 hours (fixed, `SETUP_LINK_HOURS`), used once; a `setup` link only for a pending account, a `totp_reset` link only for a `totp_reset` one. Lock the account row before the link row, the order the team actions use, or the two can deadlock. The setup checks the password against `admin.password_min_length` and a TOTP code from the last secret offered, then activates the account and issues 10 backup codes in one transaction.
- **Argon2 is the costly step:** check a token or find the account before hashing, and never hash inside an open transaction except under the account's row lock, which the lockout needs.
- **Sign-in:** password and a 6-digit TOTP code or a backup code, in one request. A TOTP time step is never accepted twice (`totp_last_step`). Every refusal answers alike (`401`), a locked account included (owner decision 2026-11-05), and takes as long as a wrong password, so neither the answer nor its time shows whether a name has an account or is locked. Attempts on one account take turns on its row lock; `admin.login_max_attempts` failures lock it for `admin.lockout_min`. All settings are read at each attempt.
- **Sessions:** the cookie `__Host-fox_drop_admin` is HTTP-only, secure, same-site strict, `Max-Age` `admin.session_max_hours`. The server ends a session after `admin.session_idle_min` without activity or `admin.session_max_hours` after sign-in, read at each check, and records the reason. OWN's actions end sessions with `forced_sign_out`, `account_disabled` or `totp_reset`.
- **Audit:** `admin_account.create`, `.setup`, `.lock`, `.roles_change`, `.disable`, `.enable`, `.force_sign_out`, `.setup_link_reissue`, `.totp_reset`, `.totp_enrol`, `admin_session.sign_in` and `.sign_out`, each in the transaction of its change, with no secret in the before and after values. The actor role is every role held, sorted and joined (`actorRole`, owner decision 2026-11-05), such as `FIN,OPS`.
- **App sign-in, one engine for every app** (owner decision 2026-11-05): `AppSignInService` and `AppSessionsService` take the party (`appParties` in `schema.ts`: `customer`, `merchant`, `captain`). Each party keeps its own account table (`customer_accounts`, `merchant_accounts`, `captain_accounts`); a new party adds its table, its value in `appParties` and the `CHECK`s, and its routes. The request and answer parts the routes share are in `app-auth.ts`. Codes, sessions, refresh tokens and signing keys are shared, with a `party` column.
- **Code sender:** `CodeSender` (`code-sender.ts`) is the port of architecture §8.3.1. Until the WhatsApp sender of the `otp-sender` process exists, the API calls it directly (owner decision 2026-11-05). `FOX_DROP_ENVIRONMENT=development` gives `DevelopmentCodeSender`, which prints the code to stdout and keeps the last one per number for the tests; any other value gives `UnavailableCodeSender`, so every request answers `503` and nothing is sent. The development sender refuses to be built elsewhere (`code-sender.test.ts`).
- **Codes** (architecture §8.3.2): 6 digits from `randomInt`, stored as an HMAC bound to the number (`signInCodeHash`), with the number's keyed hash, the device and the expiry, compared with `timingSafeEqual`. One open code per number and app (a partial unique index on `(party, phone_hash)`); the resend wait is per number whatever the app. A request takes the number's advisory lock, ends the open code as `replaced`, and sends last, so a refused send rolls the new code back and releases its limits. A code is used only by the device that asked for it. A wrong code counts at once; `otp.max_attempts` wrong ones end it. Every `otp.*` setting is read at each request. The answer to a code request is the same whether the number has an account or not.
- **Request limits** (architecture §8.3.3 item 2): rolling windows in Valkey sorted sets, checked and recorded in one Lua step (`request-limits.ts`), so parallel requests cannot all pass: the IP address per hour (every request it lets through counts, those refused later included; one it refuses does not, so `Retry-After` is honest), then, under the number's lock, the number per day and per hour and the device per day (only codes sent). Refusals answer `429` with `error` and `Retry-After`: `resend_wait`, `hourly_limit`, `daily_limit` (the number's or the device's, «تجاوزت عدد المحاولات المسموح…»), `ip_limit`. `not_on_whatsapp` answers `400`, `unavailable` `503`. App Check (§8.3.3 item 1) comes with the real sender.
- **Tokens** (architecture §15.1): the access token is an EdDSA JWT for 15 minutes (`ACCESS_TOKEN_MINUTES`), audience the party, subject the account, `sid` the session, `kid` the key. Keys are `app_signing_keys` rows, the private key encrypted with `IdentitySecrets`; a new one every 30 days (`KEY_ROTATION_DAYS`, owner decision 2026-11-05), created under an advisory lock, one load shared by concurrent callers; a key verifies until 15 minutes after its successor takes over; an unknown `kid` reads the keys at most every 10 seconds. Resolve the signing key (`AppSessionsService.signingKey`) and read the settings before opening a transaction: loading them takes a pool connection of its own, and a transaction waiting for a second one can exhaust the pool. The guard checks the token, then that its session is still open (a key read), so a sign-out applies at once (CU §5.4). The refresh token is a random token stored as SHA-256, used once; presenting a used one ends its session (`refresh_reuse`), which kills the whole family. Owner decision 2026-11-05: a used token presented again within `REFRESH_RETRY_GRACE_SECONDS` (10) of its first use, while it is still the session's `last_used_token_id` (no clock comparison between servers), is a retry whose answer was lost: it gets a new pair, and the session's unused token is marked `superseded_at`, so one token stays live; a superseded token presented later is a reuse. The refresh locks the session row, then the token, so refreshes of one session take turns and never deadlock. A server older than the grace ignores `superseded_at`, so never serve old and new versions side by side once apps refresh. A refresh also checks that the account is still active.
- **Customer account states:** only `active` exists so far, and sign-in looks for the number's `active` account. When the account states of CU §5.5 arrive, a blocked or review-stopped customer still signs in to the same account (only «مغلق» frees the number), so the sign-in and the refresh look for any account that is not closed.
- **Restaurant users** (RA §5.1, `merchant-accounts.service.ts`): `merchant_accounts` rows, an owner or a cashier of one restaurant, never created by sign-in (no self-signup); `addAccount` (OPS and the seed so far) takes a Syrian or Turkish mobile like the sign-in routes (`app-phone.ts`), refuses a number another account not removed holds (S6, `phone_taken`, under the number's advisory lock and a partial unique index) and audits `merchant_account.create` without the phone. The restaurant and city are plain columns: `identity` reads the restaurant's status and its devices through `MerchantsService`, and `merchants` imports only types from `identity`, so there is no cycle.
- **Restaurant sign-in** (RA §5.2, §5.5): architecture §8.3.2 lets RA §5.2 items 3–4 show their messages, and §8.3.3 sends codes to real users only, so the code request answers `403` `not_registered`, `restaurant_draft` or, for a cashier, `restaurant_terminated` without sending (`merchantSignInRefusal`); the IP limit still counts it. The sign-in checks again and refuses a status changed since, using up the code. A suspended restaurant signs in; a terminated one's owners too, and the `merchants` routes keep them to the money section. The status is read outside any transaction (a pool connection of its own): at the code request, the sign-in, every refresh and every request (`authenticate`), so a cashier's access ends as soon as the restaurant is terminated. `AppSession.merchant` carries the account's restaurant and role.
- **Captain accounts** (CA §4.9, `captain-accounts.service.ts`): one `captain_accounts` row per captain record, never created by sign-in; `addAccount` (OPS and the seed so far) takes a Syrian or Turkish mobile, refuses a number another captain holds (`phone_taken`) and a second number for a captain (`account_exists`), under advisory locks and unique indexes, and audits `captain_account.create` without the phone. The captain is a plain column: `identity` reads the captain's status through `CaptainsService`, and `captains` imports only types from `identity`.
- **Captain sign-in** (CA §4.9; owner decision 2026-11-06): the code request answers alike for every number, as architecture §8.3.2 asks: every step runs (the limits, the resend wait, the code row), but only a captain who may sign in is sent the code (§8.3.3), so a number of no captain or a terminated captain gets nothing and a guessed code is a wrong code. The joining slice sends codes to new numbers for the application form (CA §5.1). Once the right code proves the number, the sign-in refuses a contract ended since with `403 contract_ended`. A suspended captain signs in and sees the suspension. A terminated captain's sessions stop at once: the status is read at the sign-in, every refresh and every request (`authenticate`); the session rows stay open until the panel's offboarding ends them. One device (K5): a captain's sign-in ends the sessions of their other devices with `other_device`; the old device's next call or refresh answers `401 other_device` (`SignedInElsewhereError`, `RefreshRefusedError.reason`), so the app shows «سُجّل دخولك من جهاز آخر». `AppSession.captain` carries the account and its captain. Refusing a second device during an active order (CA §4.9) and OPS releasing the device (AP §9.7.5) come with the ordering slices and the panel.
- **Restaurant devices** belong to `merchants` (`MerchantsService.nameDevice`, `deviceNamed`); `PUT /v1/merchant/auth/device` names the device, and `deviceNamed` in the sign-in and session answers tells the app to ask for the name (RA §5.2 item 5).
- **App sessions:** one per device and app: a new sign-in on a device ends the device's earlier session (`new_sign_in`). Sessions never expire with inactivity (CU §5.4); they end on sign-out, sign-out everywhere, or refresh reuse. `AppSessionsService.endAll` is the call for blocking, closing and forced sign-out, inside their transaction.
- **App routes:** `@AppSignedIn()` with `@CurrentAppSession()`, or `@AppSignedInOrGuest()` with `@OptionalAppSession()` for a route guests may call too (no `Authorization` header runs it as a guest) (`src/http/access.ts`); `RouteAccessGuard` reads `Authorization: Bearer <access token>` and checks its audience against the route group's party. No valid token answers `401`; an app route outside an app group `403`.
- **Time:** services take `now` and never read the database clock, so tests move time by passing it.
