# notifications module

Push, in-app messages, real-time publishing and sound levels (architecture §4.2). So far real-time publishing through Centrifugo, its connection tokens and its subscription proxy (architecture §6.1–6.2; RA §4.3; CU §4.3), the panel's alerts (AP §7.3, §9.1.3), and push on Android through FCM with the customer's stored notifications (architecture §8.1; CU §13–14; slice 2.3a).

## Rules

- **Centrifugo** holds the WebSocket connections; the API stays stateless (§6.1). Its channels are `infra/centrifugo/config.yaml`, mounted by the local `compose.yaml`, the tests (`src/centrifugo/test-centrifugo.ts`) and each environment's `infra/compose.yaml`; its secrets and subscription proxies come from the environment. A new namespace goes into that file, `NAMESPACE_PARTY` in `realtime-access.ts` and `channels.ts`.
- **Configuration** (`realtime-config.ts`), read at each call, each process what it uses: the API signs tokens with `CENTRIFUGO_TOKEN_SECRET` and its guard checks `CENTRIFUGO_PROXY_SECRET`; the API and the worker call Centrifugo's HTTP API with `CENTRIFUGO_API_URL` and `CENTRIFUGO_API_KEY`. Without them real time is off: the token routes answer `503 realtime_unavailable`, the proxy refuses every call, and the worker logs it and leaves the outbox as it is. In production a missing one stops the process at start (`requireRealtime`), since restaurant devices ring only through it (RA §4.3). No secret ships in an app (E7).
- **Connection tokens** (`realtime-tokens.ts`): `POST /v1/merchant/realtime/token`, `POST /v1/customer/realtime/token` and `POST /v1/captain/realtime/token` (`@AppSignedIn()`) and the panel's `POST /v1/admin/realtime/token` (`@SignedIn()`, its cookie on its own origin, so no secret is in the bundle) answer an HS256 JWT for 15 minutes (`CONNECTION_TOKEN_MINUTES`, as long as an access token). Its subject is the app or panel session, so Centrifugo's user is one device's or one browser's session; its `meta` is the party (`admin` for the panel) and the account, which Centrifugo passes only to the proxy (`include_connection_meta`). The app asks again when Centrifugo says it expired. A terminated restaurant's owners get `403 restaurant_terminated` (RA §5.5).
- **The subscription proxy** (`realtime-access.ts`): Centrifugo asks the API about every subscription, by namespace: `merchant` calls `POST /v1/merchant/realtime/subscribe`, `order` calls `POST /v1/customer/realtime/subscribe`, `captain` calls `POST /v1/captain/realtime/subscribe`, `ops` calls `POST /v1/admin/realtime/subscribe` (the proxies `merchant`, `customer`, `captain` and `admin`). The routes are `@RealtimeProxy()`: the guard compares `X-Centrifugo-Proxy-Secret` with `CENTRIFUGO_PROXY_SECRET` in constant time, so only Centrifugo calls them, and nginx answers them with 404 from outside. They stay out of the OpenAPI document (`@ApiExcludeEndpoint()`), so no client is generated; `src/http/openapi.test.ts` fails on any other route left out of the document, or a proxy route left in. The connection's session is checked as a request's is (`AppSessionsService.openSession`): an ended or unknown one is disconnected (`4501`, the client does not reconnect with it). The channel must be the session's own: `merchant:{restaurant_id}` the restaurant user's restaurant, unless it is terminated; `captain:{captain_id}` the captain's own; `order:{order_id}` the customer's order (checked by `ordering`, which registers it with `RealtimeAccess.allow`, since this module cannot read orders). A panel session is checked with `AdminSessionsService.openSession` (open, its account active, within its idle and maximum ends, without recording activity, so an open socket never keeps an idle session alive); `ops:city.{city_id}` takes a user who sees the board (`operations.read`) or receives alerts (OWN, OPS, FIN; `readsOps`, owner decision 2026-11-08); every user has every city in V1. Anything else is refused with `403`.
- **The captain channel** (CA §15, CA §4.9): the outbox relay publishes an order's event to `captain:{captain_id}` of the captain it is about (an offer's, or the one assigned). A captain's sign-in ends the other devices' sessions inside its transaction and calls `notifyEnded` after it commits, so their connections end.
- **Sessions that end** (`realtime-sessions.ts`, CU §5.4, RA §5.1): `AppSessionsService` tells its `onEnded` listeners once a sign-out, a sign-out everywhere or a refresh reuse commits (`AdminSessionsService` once a panel sign-out commits, and once a force sign-out, a disable or a TOTP reset commits: `endAll` returns the ids the team service passes to `notifyEnded`; a role change calls `notifyAccessChanged`, which disconnects the account's open sessions with `4001`, so the panel reconnects and the proxy checks the new roles, AP §6.1), and this module disconnects each session's connections through Centrifugo's `disconnect` API, without making the sign-out wait or fail. A session ended inside another module's transaction (`endAll`) is disconnected when that module calls `notifyEnded` after its commit.
- **Calling Centrifugo** (`realtime-publisher.ts`): `broadcast` (with an idempotency key, so a repeat within a few minutes is dropped) and `disconnectSession`, 2 s each. A failure throws `PublishFailedError`: `answered` when Centrifugo refused the call, not when it was out of reach, failed (any HTTP error status) or answered something unreadable. The outbox relay in `ordering` and this module's alerts and platform relays are the only publishers; the worker gets it from `NotificationsWorkerModule`.
- **History and recovery** (§6.1): each namespace keeps recent publications (`history_size`, `history_ttl` 10 minutes) and the apps' force recovery, so a client that reconnects with its offset gets what it missed; when it cannot, it fetches the full state (RA §4.3). `ops` forces none: the panel fetches the full state after every subscription (§10.3). Centrifugo's engine is memory, so a Centrifugo restart loses history, and clients fetch the full state.
- **The ops channel** (`ops:city.{city_id}`, §6.2, §10.3; owner decision 2026-11-08: every order event and every alert change): the orders' relay publishes each order event there (`ordering`'s `outbox-relay.ts`), and every alert raised, acknowledged or resolved is a row of `notifications.alert_outbox` written by `AlertsService` in the change's own transaction (E4; the application role inserts and may change only `published_at`). The worker's `AlertsRelay` (`AlertsWorkerModule`) publishes them every `ALERTS_RELAY_MS` (1 s; many modules' transactions write them, so a poll of the unpublished index wakes it rather than a job in each), as the orders' relay does: id order, `FOR UPDATE SKIP LOCKED`, idempotency key `alert-outbox:<id>`; an alert of the whole platform goes to every active city. An alert's publication is its type, the alert's id and its time, never its rule (some subscribers, SUP, do not receive it, AP §7.3); the panel reads the list and the board again, which answer what its roles see. `AlertsService.sync` takes a transaction, never the pool, so a change and its row commit together; the sweep opens one per subject. A row Centrifugo refuses is logged once. Browsers connect only from the panel's origin (`CENTRIFUGO_CLIENT_ALLOWED_ORIGINS` in each compose file).
- **Platform broadcasts (RA §18, CA §15, AP §7; slice 2.4c, `platform-broadcasts.ts`, `platform-relay.ts`):** `PlatformBroadcasts.enqueue(tx, broadcast)` writes a row of `notifications.platform_outbox` in the change's transaction (E4; the application role inserts and may change only `published_at`): `platform.emergency_stop` (a city's stop started or ended, `active`) for the restaurant and captain apps and the panel, written by `ordering`; `platform.app_changed` (an app's `app.<app>.*` setting changed, `app`) for that app in every active city, written by `AppChangeBroadcasts`, which `SettingsService.onChanged` calls in the setting's transaction; `captain.availability_changed` (`captainId`; slice 2.13a) for one captain's own channel only, written by `CaptainAvailabilityNotices` in the transaction of a force offline or of a last order that ended the online period (`CaptainsService.onAvailabilityChanged`), which also queues the force offline's push with the reason (`captain.forced_offline` at once, `captain.forced_last_order` during an order; CA §14 #26). The worker's `PlatformRelay` (`PlatformRelayWorkerModule`, every `PLATFORM_RELAY_MS`, 1 s) publishes each row as the alerts relay does to every restaurant's `merchant:{id}` (`MerchantsService.restaurantIds`) and captain's `captain:{id}` (`CaptainsService.captainIds`) channel of the city, `ops:city.{id}` when `ops`, and `order:{id}` of each order the row names (the customer's tracking screen, AP §9.1.6 item 2), at most 500 channels per call, each call keyed `platform-outbox:<id>:<offset>`. A publication is its type and payload (`schema`, `active` or `app`, `at`): a fact the client reads again in full (the stop route, or `GET /v1/{app}/platform`), so a missed one is never the only copy. A browsing customer gets none until the `customer:` channel: the app reads the stop on opening.
- **Restaurant state changes (RA §18, §16 #3, #24, #25; slice 2.6a, `restaurant-state-relay.ts`):** the worker's `RestaurantStateRelay` (`PlatformRelayWorkerModule`, woken by each change's `QUEUES.restaurantStateRelay` job, and once a minute) takes `merchants.state_outbox` through `RestaurantStatusService.relayStateChanges`, queues the push of `restaurantStatePush` (the auto-pause, a pause that ended on its own while the restaurant takes orders again, busy mode's reminder, and operations' pause, resume and end of busy mode, #23; source `merchants-state:<id>:<template>`, so a repeat pushes once) and publishes `restaurant.state_changed` (`schema`, `restaurantId`, `kind`, `values`, `at`) to `merchant:{id}` and `ops:city.{id}` (key `merchants-state:<id>`). A change with `endedAuto` resolves the restaurant's «مطعم أوقف تلقائياً» in a transaction of its own (`AlertsService.sync`), before the sweep would, unless an auto-pause holds the restaurant again by then (`RestaurantStatusService.isAutoPaused`: the row may be relayed late or again). Every device reads its status again on it. While real time is off the worker logs it and the rows wait, with their pushes, as the orders' outbox does.
- **Alerts (AP §7.3, §9.1.3; owner decisions 2026-11-07: slice 2.2 in two pull requests):** `notifications.alerts`, one row per alert, kept after it closes as the history. `alert-rules.ts` is the catalogue built so far: each rule's code, severity, recipient roles, subject (`order`, `captain`, `otp_pool`, `otp_number`) and whether it resolves itself; each later alert joins it with its slice. The module that owns a condition calls `AlertsService.sync(executor, subject, evaluated, open, now)` in its own transaction: it raises the codes of `open` not open for the subject and resolves the open ones of `evaluated` no longer in `open`. A partial unique index keeps one open alert per rule and subject, so two syncs at once leave one. A rule whose condition never clears (`away_from_address`, information) is raised once per subject and closes with its acknowledgment (an arrival away and a delivery away on one order are one alert). The subject's `details` (the order number, the captain's or the restaurant's name) go with every alert raised; `codeDetails` adds what one rule's alert carries (slice 2.13c: «طوارئ كابتن» the location sent, `latitude`, `longitude`, `locatedAt`, which the list answers as `location`). `GET /v1/admin/alerts?cityId=&state=open|closed` (`@SignedIn()`): the open alerts of the city and of the whole platform (`city_id` null) that the session's roles receive, by severity then age, or the latest 100 closed; `POST /v1/admin/alerts/{alertId}/acknowledge` («استلام», `@SignedIn()`) assigns it to the first recipient who takes it; a later call answers it with who took it, so it needs no `Idempotency-Key`. An alert the roles do not receive is `404`. The answer names who took it (`AdminSessionsService.names`).
- **Who syncs what:** `ordering` syncs an order's alerts (`order-alerts.ts` there); the worker's `AlertsSweep` (`AlertsWorkerModule`, every `ALERTS_SWEEP_MS`, 30 s) reads what no transaction of ours changes: the code senders' health (`OtpSenderPoolService.read`, through `OtpSenderPoolModule`; skipped in development, whose codes go to stdout with no number) for «لا يمكن إرسال رموز الدخول» and «رقم إرسال الرموز متوقف», each city's captains at their cash limit (`CaptainsService.cashLimits`, at current rates) for «كابتن بلغ حد العهدة», and each city's auto-paused restaurants (`RestaurantStatusService.autoPaused`, subject `restaurant` with its name) for «مطعم أوقف تلقائياً», resolved once operations resume it. A subject it no longer sees (a number disabled, a captain terminated) has its alert resolved; a captain whose cash cannot be read keeps its alert as it was.
- **Push tokens (architecture §8.1, `push-devices.ts`):** `PUT /v1/{customer,merchant,captain}/push-token` (`@AppSignedIn()`, `{ token, platform: 'android' }`, no `Idempotency-Key`: it sets a value) registers the app installation's token, its Firebase Installation ID (FID; `firebase_messaging` 17 deprecates FCM's registration tokens, and the sender targets `fid`), at every start, at sign-in and whenever Firebase registers it again: one `notifications.push_devices` row per app session, with the restaurant and role or the captain as the session had them. A token belongs to one live row: registering it ends any other (`token_moved`); a token FCM answers `UNREGISTERED` is ended `token_invalid`. `PushDevices.targets` gives a recipient's live tokens (a customer's account, a restaurant's devices or its owners' alone, RA §16 «Owners», a captain) whose sessions are still open (`OpenAppSessions` from identity, a module of its own so the worker reads it without the API's routes), so a signed-out device gets nothing.
- **The queue (`push-queue.ts`, E4):** a module queues pushes with `PushQueue.enqueue(tx, pushes, now)` in the transaction of what they tell: `notifications.push_messages`, one row per push and recipient with the rendered text, the template, the level (the Android channel the app created for its sound, architecture §8.2), the priority, the data a tap opens (`target` and its ids, as strings) and `expires_at`: from `at`, the moment of what it tells (the queuing time when left out), `PUSH_TTL_SECONDS` later (10 minutes: a push about an order's step is no use later), or its own end (`expiresAt`, an offer's). So a backlog queued late keeps its time in «الإشعارات» and is never sent stale. Its `source` is unique, so queuing again adds nothing. `PushQueue.resend` queues again, as a new push, the latest of an order's pushes to a recipient among the templates the caller names («إعادة إرسال الإشعار»).
- **The push relay (`push-relay.ts`, `PushWorkerModule` in the worker):** every `PUSH_RELAY_MS` (1 s) claims the due rows in a short transaction (`FOR UPDATE SKIP LOCKED`, moving their next attempt `LEASE_MS`, 2 minutes, ahead so no other run takes them), then, outside any transaction, reads their devices and sends each to every live token of its recipient through `PushSender` (`fcm-sender.ts`, FCM's HTTP v1 API: a notification with the title `FOX DROP`, the body, `android.priority` and `channel_id`, and the data with `messageId`). A push that reached a device, or found none, is `sent_at` with its `devices` count; one whose devices all failed for a passing reason (`retry`: FCM busy, out of reach, 401, 429, 5xx) is tried again after `retryDelayMs` (2 s doubling to a minute) until it expires (`gave_up_at`); each outcome and its invalid tokens are written in a transaction of their own. FCM refusing the message itself is logged; `UNREGISTERED`, `SENDER_ID_MISMATCH` and an `INVALID_ARGUMENT` that names the target (`message.fid` or `message.token` in its field violations: a malformed FID) end the token; any other `INVALID_ARGUMENT` refuses the message, which is logged and ends no device. The sender signs a JWT with the service account's key (`jose`) for an OAuth token kept until 5 minutes before its hour ends; Google refusing the account (a revoked key, the API turned off) is logged and reported once per outage, and every push retries until it expires.
- **Configuration:** `FCM_SERVICE_ACCOUNT`, the Firebase service account's JSON key in base64, read by the worker only (E7: never in the repository or an app; the `deploy` skill says how the owner sets it on staging). Without it push is off: the worker logs it and the pushes wait and expire; production refuses to start.
- **«الإشعارات» (CU §13, §14: every push is also stored):** a customer's rows are their notifications: `GET /v1/customer/notifications` answers those of the last `INBOX_DAYS` (30, fixed), newest first, with the data a tap opens.
- The proof is `src/modules/ordering/order-realtime.test.ts`: a real Centrifugo, the API on a real port behind its proxy, and `centrifuge` clients.
