# notifications module

Push, in-app messages, real-time publishing and sound levels (architecture §4.2). So far real-time publishing through Centrifugo, its connection tokens and its subscription proxy (architecture §6.1–6.2; RA §4.3; CU §4.3).

## Rules

- **Centrifugo** holds the WebSocket connections; the API stays stateless (§6.1). Its channels are `infra/centrifugo/config.yaml`, mounted by the local `compose.yaml`, the tests (`src/centrifugo/test-centrifugo.ts`) and each environment's `infra/compose.yaml`; its secrets and subscription proxies come from the environment. A new namespace goes into that file, `NAMESPACE_PARTY` in `realtime-access.ts` and `channels.ts`.
- **Configuration** (`realtime-config.ts`), read at each call, each process what it uses: the API signs tokens with `CENTRIFUGO_TOKEN_SECRET` and its guard checks `CENTRIFUGO_PROXY_SECRET`; the API and the worker call Centrifugo's HTTP API with `CENTRIFUGO_API_URL` and `CENTRIFUGO_API_KEY`. Without them real time is off: the token routes answer `503 realtime_unavailable`, the proxy refuses every call, and the worker logs it and leaves the outbox as it is. In production a missing one stops the process at start (`requireRealtime`), since restaurant devices ring only through it (RA §4.3). No secret ships in an app (E7).
- **Connection tokens** (`realtime-tokens.ts`): `POST /v1/merchant/realtime/token` and `POST /v1/customer/realtime/token` (`@AppSignedIn()`) answer an HS256 JWT for 15 minutes (`CONNECTION_TOKEN_MINUTES`, as long as an access token). Its subject is the app session, so Centrifugo's user is one device's session; its `meta` is the party and the account, which Centrifugo passes only to the proxy (`include_connection_meta`). The app asks again when Centrifugo says it expired. A terminated restaurant's owners get `403 restaurant_terminated` (RA §5.5).
- **The subscription proxy** (`realtime-access.ts`): Centrifugo asks the API about every subscription, by namespace: `merchant` calls `POST /v1/merchant/realtime/subscribe`, `order` calls `POST /v1/customer/realtime/subscribe` (the proxies `merchant` and `customer`). The routes are `@RealtimeProxy()`: the guard compares `X-Centrifugo-Proxy-Secret` with `CENTRIFUGO_PROXY_SECRET` in constant time, so only Centrifugo calls them, and nginx answers them with 404 from outside. They stay out of the OpenAPI document (`@ApiExcludeEndpoint()`), so no client is generated; `src/http/openapi.test.ts` fails on any other route left out of the document, or a proxy route left in. The connection's session is checked as a request's is (`AppSessionsService.openSession`): an ended or unknown one is disconnected (`4501`, the client does not reconnect with it). The channel must be the session's own: `merchant:{restaurant_id}` the restaurant user's restaurant, unless it is terminated; `order:{order_id}` the customer's order (checked by `ordering`, which registers it with `RealtimeAccess.allow`, since this module cannot read orders). Anything else is refused with `403`.
- **Sessions that end** (`realtime-sessions.ts`, CU §5.4, RA §5.1): `AppSessionsService` tells its `onEnded` listeners once a sign-out, a sign-out everywhere or a refresh reuse commits, and this module disconnects each session's connections through Centrifugo's `disconnect` API, without making the sign-out wait or fail. A session ended inside another module's transaction (`endAll`) is disconnected when that module calls `notifyEnded` after its commit.
- **Calling Centrifugo** (`realtime-publisher.ts`): `broadcast` (with an idempotency key, so a repeat within a few minutes is dropped) and `disconnectSession`, 2 s each. A failure throws `PublishFailedError`: `answered` when Centrifugo refused the call, not when it was out of reach, failed (any HTTP error status) or answered something unreadable. The outbox relay in `ordering` is the only publisher; the worker gets it from `NotificationsWorkerModule`.
- **History and recovery** (§6.1): each namespace keeps recent publications (`history_size`, `history_ttl` 10 minutes) and forces recovery, so a client that reconnects with its offset gets what it missed; when it cannot, it fetches the full state (RA §4.3). Centrifugo's engine is memory, so a Centrifugo restart loses history, and clients fetch the full state.
- The proof is `src/modules/ordering/order-realtime.test.ts`: a real Centrifugo, the API on a real port behind its proxy, and `centrifuge` clients.

## Not yet

- `captain:`, `customer:`, `ops:` and `ops_map:` channels (§6.2), with their first publishers. A captain's sign-in that ends their other device's session (`other_device`) runs inside the sign-in's transaction and calls no `notifyEnded` yet; the captain channel's slice adds it.
- The termination of a restaurant does not end its sessions, so its devices' connections stop at their token's expiry (15 minutes); the termination's slice disconnects them.
- Presence and the restaurant devices' heartbeats (RA §4.3, §4.6, architecture §6.3), owner decision 2026-11-06: later, with the receiving-device rule. The connection's user being the session makes presence per device.
- Push (FCM, APNs), owner decision 2026-11-06: later; the outbox relay is where it joins, and AP §8.3's apology on an automatic cancellation with it.
- A Valkey engine for Centrifugo, so history survives a restart and several Centrifugo nodes share it.
- `allowed_origins` for the web apps' connections (the panel's live board).
