# content module

The texts and reason lists of AP §9.13, edited in the panel and read by the apps (architecture §4.2). The terms and privacy versions (slice 2.4b), canned replies (2.23) and categories (2.27) join with their slices.

## Rules

- **The lists** (`lists.ts`): every list of AP §9.13 «قوائم الأسباب», «الملاحظات الجاهزة» (`order_note`) and the rating reasons by stars (`*_rating_low` 1–2, `_mid` 3, `_high` 4–5), plus two lists nobody picks from that carry customer texts only (`failed_outcome`, `system_cancellation`). Each says which apps read it, whether its reasons carry «نص للزبون» (`customerText`) and whether it is `closed` (no reason can be added, since the code acts on each one). A new list goes into `lists.ts`, the migration's seed and, when an app reads it, `app-content.controller.ts` (`content.test.ts` keeps the three equal).
- **Reasons** (`content.reasons`): a stable `code` (snake_case; one added in the panel gets `custom_<8 hex>`), the Arabic `label`, the `customer_text`, `note` (`none`, `optional` or `required`: «أخرى» requires its text, CU §11.5 «سبب آخر» and CU §12.2's problems take an optional one; a closed list's reasons take none), `fixed` (the code acts on it, such as «مشكلة في مبلغ الاستلام»: it cannot be removed), `active`, `position` and, on the `reassignment` list only (a `CHECK`; `400 invalid_value` otherwise), `captain_fault`, the reason's default fault, which the reassignment dialog prefills and the admin may change (AP Appendix B, owner decision 2026-11-10; seeded by migration 0050: «طلب الكابتن» and «تأخر الكابتن» with the fault). The panel's lists carry `fault` for the list that has it. The defaults are AP Appendix B and CU Appendix C, seeded in `migrations/0029_content_reason_lists.sql`.
- **Removing** (owner decision 2026-11-07) sets `active` false: the reason is hidden from new choices and kept as recorded on past orders. Nothing is deleted.
- **Choosing** (owner decision 2026-11-07): a module that records a reason calls `ContentService.choose(list, { code, note })` before its transaction and keeps the answer's code and label (a copy, so a later rename leaves past orders as they were) and note. It refuses `unknown_reason` (not an active reason of that list), `reason_note_required` (a required note missing) and `reason_note_not_allowed` (a note on a reason that takes none); ordering answers them `400`.
- **Customer texts:** `customerText(list, code)` gives the stored text, or «نعتذر، لم نتمكن من إكمال طلبك» (`GENERIC_CUSTOMER_TEXT`, CU Appendix C). An order copies it when it is cancelled (`cancel_customer_text`).
- **Texts** (`content.texts`, one row per key): `faq.customer`, `faq.captain`, `faq.merchant` (`[{ question, answer }]`), `captain_work_rules` (`{ body }`, plain text with one rule per line) and `contact` (`{ phone, whatsapp }`). The FAQs and the work rules start from a draft written from the specs for the owner to edit (owner decision 2026-11-07).
- **Contact info:** the stored numbers, else `SUPPORT_PHONE_NUMBER` and `SUPPORT_WHATSAPP_NUMBER` (owner decision 2026-11-07); a missing or malformed number (not E.164) is left out, and the app hides its button. `GET /v1/{merchant,captain,customer}/contact` is public; its fields are optional, not nullable (Nest's OpenAPI document reads a top-level nullable type as a list).
- **The apps' read:** `GET /v1/{merchant,captain,customer}/content` (public: the captain's work rules show before sign-in, CA §5) answers the app's lists (active reasons in order, `{ code, label, note }`), its FAQ set and, for the captain, `workRules`.
- **The panel** (`/v1/admin/content`, AP §6.2): `GET reasons` (`content.read`: OWN, OPS), `POST reasons/{list}`, `PUT reasons/{list}/{code}`, `POST reasons/{list}/order` (`content.manage`: OWN); `GET faqs` (`content.read` or `content.faqs`), `PUT faqs/{audience}` (`content.faqs`: OWN, SUP); `GET texts` (`content.read`), `PUT work-rules`, `PUT contact` (`content.manage`). Two active reasons of a list never share a label. Every edit takes the list's or key's advisory lock and is audited in its transaction (`content.reason.create`, `content.reason.update`, `content.reason.reorder`, `content.text.update`, target type `content`).
- **Notification templates** (AP §9.13 «نصوص الإشعارات», slice 2.3a): `notification-templates.ts` is the catalogue of every push of CU §14, RA §16 and CA §14 that has a text, keyed `<audience>.<event>`: its spec row, default text, variables (`{name}`, as the specs write them), sound level and priority (architecture §8.1–8.2; neither editable; high only for new orders, pickup requests, offers, cancellations and arrival). `notification-templates.test.ts` checks every template has its event's name in the panel's `ar.json`. An edit is a `content.texts` row `notification.<key>` (`{ text }`), audited as `content.text.update`; it may use only the template's variables (`400 unknown_variable`), up to 300 characters. `GET /v1/admin/content/notifications` (`content.read`) and `PUT /v1/admin/content/notifications/{key}` (`content.manage`, `404 unknown_template`). `NotificationTexts.render(key, values)` gives the text in use filled with the values (a value missing leaves its placeholder), with the level and priority; the ordering module renders each push with it. A new push adds its row to the catalogue and its event's name to the panel's `content.notifications.event`.
- **Terms and privacy (AP §9.13 «الشروط والخصوصية», slice 2.4b):** `content.terms_versions`, one document per audience (`customer`, `captain`, `merchant`), versioned from 1; the newest is in force. `content.terms_acceptances`, which version each app account (identity's id, a plain column) accepted and when. Both are append-only (`UPDATE` revoked). Version 1 of each is a draft written from the specs (migration 0036), for the owner to replace before launch (owner decision 2026-11-08). `TermsService` (`terms.service.ts`): `current`, `pending(audience, accountId)`, `accept` (the version the app showed; `terms_outdated` when another is in force; again is a no-op), `acceptCurrent` (in the caller's transaction: the customer's sign-up tick, CU §5.3) and `publish` (the next version, `terms_unchanged` for the text in force, the audience's advisory lock, audited `content.terms.publish` with target `terms.<audience>`). One acceptances table for the three parties, here with the versions it points to: the accounts are identity's, so no party module owns them better. What a pending version blocks is each party's: the customer's quote (`terms_pending`, ordering), the captain's going online (`terms_not_accepted`, captains), the restaurant owner's screens other than Orders (the app, S13). Routes (`terms.controller.ts`): `GET /v1/{customer,captain,merchant}/terms` (`@AppSignedInOrGuest()`: the version in force with `pending`, false for a guest and for a restaurant's cashier, who never accepts, S13), `POST /v1/{party}/terms/accept` (`{ version }`, `@AppSignedIn()`, `409 terms_outdated`, no `Idempotency-Key`: accepting again changes nothing); the panel's `GET /v1/admin/content/terms` (`content.read`) and `POST /v1/admin/content/terms/{audience}` (`{ body }`, plain text up to 20 000 characters, `content.manage`, `400 terms_unchanged`).
- **No cache yet:** the lists are read from PostgreSQL at each request; they are small and change rarely.
