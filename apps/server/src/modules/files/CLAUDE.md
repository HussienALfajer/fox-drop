# files module

Uploads to the object storage and their checks before a record links them (architecture §4.2, §5.8; slice 2.5). The storage is Garage (T7); its setup and the tests' Garage are in the shared `src/storage/`.

## Rules

- **Two buckets:** `public-media` (`PUBLIC_MEDIA_BUCKET`), served by imgproxy under `/media/` (`infra/imgproxy/imgproxy.env`), and `private-docs` (`PRIVATE_DOCS_BUCKET`, slice 2.19g), which only the server's key reaches (the reader key has no right there). `putPrivate(key, body, type)` writes a file the server made (the reporting module's Excel exports, under `exports/`), `privateDownloadUrl(key, fileName, seconds)` signs a GET on the panel's origin (path style, `/private-docs/exports/<file>`, which nginx and Vite forward to Garage for GET only) that saves it under its name (`ResponseContentDisposition`, RFC 6266 with an ASCII fallback), and `deletePrivate(key)` removes it. The captain documents (2.34) join it.
- **Uploads** (`files.uploads`): `POST /v1/admin/uploads` (`{ purpose, contentType, sizeBytes }`) records an upload and answers a pre-signed `PUT` to `incoming/<uuid>.<ext>`, valid `UPLOAD_URL_SECONDS` (10 minutes). The type and the size are signed (`signableHeaders`), so Garage refuses any other body with `403`. Types: JPEG, PNG, WebP; at most `MAX_IMAGE_BYTES` (8 MB). Who may ask: `RESTAURANT_PROFILE` (`restaurants.manage` or `restaurants.create`: OWN, OPS and DATA, AP §9.6.3 step 1) for `restaurant_logo` and `restaurant_cover`, `restaurants.menus` for `item_photo`, `content.categories` for `category_image` (a category's icon or image, slice 2.27a, published in `content/categories/`), `marketing.banners` for `banner_image` (a banner's image, slice 2.27c, published in `marketing/banners/`), `restaurants.create` for `restaurant_contract` and `restaurant_licence` (a restaurant's scans, AP §9.6.3 step 5, slice 2.30a: in `private-docs`, published in `restaurants/contracts/` and `restaurants/licences/`, signed for the panel's origin under `/private-docs/incoming/`, which nginx on the panel's host forwards for PUT only, and shown by `privateImageUrl` under `/private-docs/restaurants/`, GET only) (`403` otherwise). No `Idempotency-Key`: the answer is a URL to upload with, never stored (like a secret shown once), and asking again makes another upload, of which only the linked one is used.
- **Where the panel uploads:** the URL is signed for `ADMIN_PANEL_URL`'s origin, path style (`/public-media/incoming/<file>`). nginx on the panel's host (and Vite in development, with `changeOrigin: false`) forwards that path to Garage with the same `Host`, so the signature holds and the browser needs no CORS. The apps' uploads sign for `APP_UPLOAD_URL` (below).
- **A report's photo (CU §12.2, §9.5; slice 2.24a, owner decision 2026-11-17):** the purpose `report_photo` lives in `private-docs` (`incoming/` then `tickets/photos/`). `POST /v1/customer/uploads/report-photo` (`@AppSignedIn()`, `{ contentType, sizeBytes }`; the customer's account as `created_by`) signs the PUT for `APP_UPLOAD_URL`'s origin (the API's host, whose `/private-docs/incoming/` nginx forwards for PUT only; in development the Garage the emulator reaches, `http://10.0.2.2:3900`). At most `REPORT_UPLOADS_PER_HOUR` (20) an hour per account (`429 too_many_uploads`, the index `uploads_created_by`, migration 0094), so a customer cannot fill the storage. `prepare(uploadId, purpose, now, owner)` finds only the owner's upload (`upload_not_found` otherwise). `privateImageUrl(key, seconds)` signs a GET on the panel's origin (`/private-docs/tickets/`, which nginx and Vite forward for GET only) for the ticket page. The restaurant app's `POST /v1/merchant/uploads/report-photo` (slice 2.24b, RA §15; served by ordering's `merchant-reports.controller.ts`, which refuses a terminated restaurant, through `reportPhoto`) is the same, the restaurant user's account as `created_by` and its owner. The panel's `POST /v1/admin/uploads` never takes `report_photo`.
- **Linking, in two halves:** `prepare(uploadId, purpose)` before the record's transaction, since it calls the storage and must never run under a row lock (the bucket by purpose): the upload must exist (`upload_not_found`), be for that purpose (`upload_wrong_purpose`) and be at most `LINK_WITHIN_MS` (an hour) old (`upload_expired`); its file is copied from `incoming/` to its published key (`<folder>/<file>`, by purpose: `restaurants/logos`, `restaurants/covers`, `menu/items`), which no pre-signed URL covers (`upload_missing` without a file), and the copy must have the size and type asked for and start with that type's signature (`hasImageSignature`; `upload_invalid`). A purpose in `EXACT_IMAGE_SIZES` (`banner_image`: 1200×500, owner decision 2026-11-18) must also have that pixel size, read from the first 128 KB by `imageSize` (`image-size.ts`: the PNG, JPEG and WebP headers, never a decode; `upload_invalid` without a readable size, `upload_wrong_size` otherwise). A file checked this way never changes again, though its upload URL still writes to `incoming/` for its 10 minutes. Then `link(tx, uploadId)` in the record's transaction takes the upload's lock and sets `linked_at`; it answers the published key, with `alreadyLinked: true` when an earlier call linked it: the caller treats the same key on the same record as a repeat and anything else as `upload_used`. A published key is new for every upload and never reused, so imgproxy's and nginx's caches never go stale.
- **The storage client** has short timeouts (2 s to connect, 10 s per request) and is built on first use from `STORAGE_URL`, `STORAGE_KEY_ID`, `STORAGE_SECRET` and `ADMIN_PANEL_URL`, so a process or a test that never uploads needs none of them. The SDK's default checksums are off (`WHEN_REQUIRED`): a pre-signed URL must not carry one the browser cannot send.
- **Tests:** `startTestStorage()` (`src/storage/test-storage.ts`) starts Garage with the image of `compose.yaml` and sets it up; point `STORAGE_URL`, the key and `ADMIN_PANEL_URL` at it before the app starts.
