# fx module

Currencies, a city's base and accepted currencies, rate versions, rounding and the rate snapshot an order keeps (AP §8.6, §9.10.4; architecture §4.2, §5.2).

## Rules

- **No floats:** amounts are `bigint` minor units; a rate is an exact reduced fraction (`Rate`: base major units per one major unit of the currency), stored as `rate_numerator` and `rate_denominator`. `parseRate` takes the panel's input in either direction («1 USD = 41.20 TRY» is `base_per_unit`, «1 TRY = 290 SYP» `units_per_base`), up to 18 significant digits; a rate whose numerator or denominator would not fit a PostgreSQL `bigint` is refused (`invalid_rate`).
- **Currencies are data** (`fx.currencies`): the migration seeds TRY, USD and SYP in every environment, with ISO 4217 decimals (owner decision 2026-11-05: 2 for all three). A redenomination is a new row. The application role may change a currency's status only, never its decimals.
- **A city's currencies** (`fx.city_currencies`): its accepted currencies with display order and enabled flag, the base among them (`fx.city_bases`). Once the city has a base, another currency is enabled only with a rate against it, and the base stays enabled.
- **The base currency** (D25) can change until the city's first order, and only once the city's money settings and the other modules' amounts are in the new base (`amounts_in_other_currency`, read through `SettingsService.cityAmounts` and the sources registered with `useCityAmounts`, such as geo's delivery fee rule). A change enables the new base, disables the other currencies and starts a new `epoch`: a rate counts only in the epoch it was set in, so the rates of an earlier base never come back, even when that base returns. The other currencies are enabled again once each has a rate.
- **The lock** (`snapshotForOrder`, inside the transaction that places the order): the city's first order sets `locked_at`; every order then holds a shared row lock on `fx.city_bases`, which orders share and a base change (`FOR UPDATE`) waits for, so a base change either happens before an order or is refused after it. A rolled-back order locks nothing. A trigger (`fx.city_bases_keep_lock`) refuses any change of a locked base's currency, epoch or lock, whatever the caller.
- **Rates** (`fx.rate_versions`) are append-only: a change is a new version with its editor (an admin, never the system) and an optional reason; the application role cannot update or delete one. The current rate is the newest version of the current epoch; `rateHistory` gives every version, newest first. A change above `fx.large_change_confirm_pct` from the current rate, measured in the direction the editor entered it, is refused until the caller passes `confirmLargeChange` (the screen's second confirmation).
- **Rounding** is the settings `currency.<code>.rounding_unit` (in the currency's minor units) and `currency.<code>.rounding_mode`, read through `SettingsService`, so their history, reasons and edit roles stay in one place. `roundToUnit` rounds `nearest` (a half goes up), `up` (towards +∞) or `down` (towards −∞).
- **The snapshot** (`RateSnapshot`) holds every enabled currency with its rate version, decimals and rounding rule. `snapshot` serves a quote; `snapshotForOrder(cityId, tx)` serves the order and locks the base. Every later calculation for the order uses the snapshot it kept (`equivalent` for what the customer sees in another currency, rounded by its rule; `toBase` for a payment line, to the nearest base minor unit). A currency without a rounding unit refuses the snapshot (`rounding_unit_missing`, owner decision 2026-11-05), so no order is placed until the owner enters it.
- **The settings check the city's currencies through fx:** `FxService` registers itself with `SettingsService.useCityCurrencies` when the module starts, since fx reads the rounding settings and settings cannot import fx back. A process that changes settings must import `FxModule` (the API does). Likewise a process that changes a base currency must import every module that registers with `useCityAmounts` (today `GeoModule`; the API does), or fx cannot see their amounts.
- **Every change** of a city's currencies, base or rates is audited in its transaction (`city_currency.set`, `base_currency.set`, `rate.set`); a change that changes nothing records nothing. Changes of one city's currencies and of its money settings take turns on one advisory lock (`lockCityCurrencies` from the settings module).
- **Refusals** throw `FxRefusedError` with its `refusal`; the routes and the ordering module map them to their answers.
