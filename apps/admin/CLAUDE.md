# apps/admin

The admin panel «لوحة الإدارة»: a static single-page app (architecture §10). `apps/merchant-portal` follows the same rules.

## Layout

- `src/main.tsx`: mounts the app with i18next, TanStack Query and TanStack Router.
- `src/router.tsx`: the route tree, written in code (no generated route file).
- `src/api.ts`: the API client. `src/i18n.ts` and `src/locales/ar.json`: the translations.
- One feature per pair of files (owner decision 2026-11-07, logic apart from presentation): `<feature>.ts` holds its queries, mutations and pure functions, and maps each answer to a typed result (`{ status: 'refused', refusal }` for a refusal the page explains, a thrown error for anything else); `<feature>-page.tsx` only renders. `session.ts` holds the session read, sign-in and sign-out.
- `e2e/`: the Playwright tests. Unit tests sit next to the code as `*.test.ts`; one that imports a feature file mocks `./api.js` (`vi.mock`), since the client reads `window`.

## Rules

- **API (E6):** call the server only through `api` from `src/api.ts` (`createApiClient` from `@fox-drop/api-schema`), inside a TanStack Query query or mutation. Never a hand-written `fetch`, never a second client.
- **Same origin (owner decision 2026-11-05):** the app calls `/v1` on its own origin. In development Vite forwards `/v1` to the server on port 3000 (`vite.config.ts`), so the `__Host-` session cookie works without CORS; in production the edge routes `/v1` to the API. Never put an API address, key or secret in the bundle (E7): every `VITE_` variable ships to the browser.
- **Arabic, right to left (AP §4.7):** `index.html` is `lang="ar" dir="rtl"`. Every user-facing string, the page title included, is a key in `src/locales/ar.json`, read with `t()`; the keys are typed from `ar.json`, so a missing key fails the type check. Translations use Western digits (`src/locales/ar.test.ts`). Format numbers and dates with `Intl` and the `ar-u-nu-latn` locale, never `ar` alone. The root `eslint.web.mjs` holds the lint rules every web app shares: it fails text written in JSX, in braces or in a label attribute (`alt`, `title`, `placeholder`, `aria-label` and the like), and `Intl` or `toLocale*String` called with plain `ar`. `test/lint.test.ts` proves each one fires; add a case when a rule changes.
- **Session (AP §5.1–5.2):** the cookie is httpOnly, so the panel knows its session only from `GET /v1/admin/auth/session` (`sessionQuery`, null on 401). Every page except `/sign-in` and `/setup` sits under the `signed-in` layout route, whose `beforeLoad` sends a request without a session to `/sign-in` and puts `session` in the route context. A page needing a permission checks it with `can()` in its route's `beforeLoad` and hides its links the same way (AP §6.1); the server still enforces it. A 401 from any route outside `/v1/admin/auth/` means the session ended: `api.ts` clears it and opens `/sign-in`.
- **Operations pages (AP §9.2–9.3, slice 1.14f):** `/orders` (the board, `operations.read`), its child `/orders/$orderId` (the detail, in the board's `<aside>`, so the board stays visible, AP §9.2.1) and the detail's child `/orders/$orderId/assign` (the picker, `operations.manage`). The chosen city travels as the `city` search parameter on `/orders` (its code, from `citiesQuery`; the first city without one), and links keep it with `search`. The board's filters belong to their city, and a choice whose last order left the board falls back to «الكل» (`effectiveFilter`). The board and the detail are live over the city's channel (below) and read again every `POLL_MS` (10 s, owner decision 2026-11-07) only while it is down; a command invalidates the reads it changes. Times and SLA colours use the server's clock (`clock.ts`, from every response's `Server-Time`), and times show in the city's zone. Code labels (statuses, tracks, alerts, badges, vehicles; the detail's outcomes and reasons in `order-detail.ts`) are key maps checked against the API's enums with `satisfies`; a code the panel does not know is hidden, never shown in English, and only an operator's own reason shows as written (`eventReason`). Money is formatted from minor units by `format.ts`, never through a float, with the minor-unit digits of `fx.currencies` (Intl's own data gives SYP none).
- **Content (AP §9.13, slice 2.1):** `/content` (`content.read` or `content.faqs`) holds every reason list with its reasons (label, customer text where the list has one, «أخرى» text, the default fault «بخطأ من الكابتن افتراضياً» in the list that has `fault` (reassignment, slice 2.12a), offered or not; up and down to reorder; a fixed reason cannot be removed and a closed list takes no new reason), the three FAQ sets, the captain work rules and the contact info. OWN edits everything (`content.manage`), OPS reads, SUP edits only the FAQs; a form a session cannot edit is a disabled `fieldset`. A list's Arabic name is `content.list.<list>`, keyed by the API's list enum. Removing a reason only hides it from new choices (owner decision 2026-11-07). «نصوص الإشعارات» (slice 2.3a) lists every push's text by app: the event's name is `content.notifications.event.<key>` (keyed by the API's template key; the key shows when a name is missing), its variables, its spec row and the default; only the text is edited, and «استعادة النص الافتراضي» puts the default back in the field. «الشروط والخصوصية» (slice 2.4b) shows each audience's version in force (number, date, text); OWN publishes the next one after a second press («تأكيد النشر»), since everyone of that audience accepts it again; the text in force is refused (`terms_unchanged`).
- **«التطبيقات» (AP §9.14, slice 2.4a; owner decision 2026-11-08: this group before the other settings screens of 2.38):** `/settings/apps` (`settings.read`, OWN) shows, for each of the customer, restaurant and captain apps, the minimum and latest versions, the update message and maintenance with its message (`app.<app>.*`), read from `GET /v1/admin/settings` for the first city (they are global) and saved key by key with `PUT /v1/admin/settings/{key}`, only the ones that changed; an empty field is unset, and a value the server refuses (`400`, a version not in the form `1.4.0`) stops the save there.
- **Alerts (AP §7.3, §9.1.3, architecture §10.3; slice 2.2a, owner decisions 2026-11-07):** a session holding OWN, OPS or FIN (`receivesAlerts`) gets `AlertsMonitor` on every signed-in page: the button «اضغط لتفعيل صوت التنبيهات» until a click enables the sound (browsers block audio before one; it also asks for desktop notifications) and the bell «التنبيهات: {العدد}» linking to `/alerts` (any signed-in user; the server answers what the roles receive). The sound is generated with Web Audio (`alert-sound.ts`, no files): a critical alert repeats every `CRITICAL_REPEAT_MS` (3 s) while any critical alert waits for «استلام», a warning chimes once when first heard, information is silent, and it cannot be muted (D22); a critical alert first seen while the tab is hidden shows a desktop notification (`useAlertAlarm`, `soundPlan`). The alarm watches the first city until the top bar's selector. The alerts are live over the city's channel and read every `ALERTS_POLL_MS` (10 s), in the background too, only while it is down. Alert labels are `alertKeys` in `order-labels.ts`, keyed by every code of the alerts API.
- **Real time (architecture §6.2, §10.3; slice 2.2b):** `live.ts` keeps one `centrifuge` connection to `/connection/websocket` on the panel's own origin (nginx on staging and production, Vite's proxy to the local Centrifugo in development), with a token from `POST /v1/admin/realtime/token` asked with the cookie (a 401 stops it reconnecting). A screen that shows a city's orders or alerts calls `useOpsChannel(cityId)` (the board, the alarm, `/alerts`); the screens share one subscription per city, and the connection closes when none follows a city. Every subscription, the first and each after a reconnect, reads the city's board, open details and alerts again (`cityQueries`, no recovery); an event invalidates the reads it names (`staleQueries`: an order event the board and that order, an alert change the alerts). A query of a city whose subscription is up does not poll (`pollUnlessLive`).
- **The emergency stop (AP §7, §9.1.6, slice 2.4c):** every signed-in page shows `EmergencyStopBar` above the rest: «المنصة تعمل», or «إيقاف طارئ» with its minutes by the server's clock and the attempts (`GET /v1/admin/emergency-stop`, read every `ATTEMPTS_POLL_MS`, 30 s, since the attempts have no event, and at once on the ops channel's `platform.emergency_stop`, followed only by a session the channel lets in, `followsOps`); its red, flashing look waits for the design. A session holding `emergency_stop.toggle` (OWN, OPS) gets the link to `/emergency-stop`: the dialog prefilled from the server's defaults, with a preview of the delay notice and the automatic resume typed on the city's clock (`zonedToUtc`); while a stop is on, the stop as it is and «استئناف», with the optional «الخدمة عادت» text.
- **«الصور» (slice 2.5; AP §9.6.3, §9.6.6; owner decision 2026-11-09, until the onboarding wizard of 2.30 and the menu editor of 2.31):** `/images` (`restaurants.read` or `restaurants.menus`, `canSeeImages`) picks a restaurant of the first city (`?restaurant=`, the `city` parameter as on the board), shows its logo, cover and each item's photo, and lets `restaurants.manage` or `restaurants.create` set the logo and cover (`canSetProfileImages`, AP §9.6.3 step 1) and `restaurants.menus` the photos. `useSetImage` checks the file (JPEG, PNG or WebP, up to 8 MB, `fileRefusal`), asks `POST /v1/admin/uploads`, `PUT`s the file to the signed URL, then links it with the record's route, whose refusals map to «الملف ليس صورة صالحة» or «تعذّر رفع الصورة». That `PUT` is the one `fetch` outside the API client: it goes to the storage under `/public-media/incoming/` on the panel's own origin (nginx, and Vite in development with `changeOrigin: false`, forward it with the same `Host`, which the signature covers), not to the API. Images show through imgproxy at `mediaUrl(key, width)` (`media.ts`, `/media/_/w<width>/plain/<key>` on the panel's origin, one of `MEDIA_WIDTHS`), so the Content-Security-Policy's `'self'` covers both.
- **«حالة المطاعم» (slice 2.6b; AP §9.6.5, §9.1.3; until the restaurant profile of 2.30):** `/restaurant-status` (`restaurants.read`) picks a restaurant of the first city as «الصور» does and shows its state by RA Appendix B's labels (`stateKey`: a pause by its source), the pause in force whatever the state (an operations or auto pause holds while closed, and «استئناف» shows whenever one is in force), an operations pause's message and reason, busy mode, the active orders against the maximum and the holiday close; `restaurants.manage` (OWN, OPS) gets «إيقاف مؤقت» (15, 30 or 60 min, until a time typed on the city's clock with `zonedToUtc`, or until resumed; a message to customers and a required reason), «استئناف», «إنهاء وضع الضغط», the holiday close with its reason and its end, and the maximum (empty is off). Each command answers the status, which replaces the read; the page follows the city's channel, whose `restaurant.state_changed` makes that restaurant's read stale. The open alert «مطعم أوقف تلقائياً» carries «استئناف» for `restaurants.manage` and a link to the page.
- **«إعادة إرسال الإشعار» (AP §9.3.2, slice 2.3a):** the order detail shows a button per party (`resendTargets`: an active order's customer and restaurant, and its captain once assigned) to a session holding `operations.manage` or `operations.compensate` (OWN, OPS, SUP; `canResend`), then the text pushed again or the refusal.
- **On the restaurant's behalf (AP §9.3.2, slice 2.7b):** while an order is placed, the detail carries `onBehalf` (the restaurant's prep-time chooser, its rejection reasons from Content and the busy-mode minutes), and a session holding `operations.manage` (`canDecide`) gets «قبول نيابة عن المطعم» (the chips or any whole minute within the floor and ceiling, `prepTimeFits`) and «رفض نيابة عن المطعم» (a reason; for «صنف غير متوفر» the order's items, each «حتى الغد» or «حتى أعيده»; for «ضغط طلبات» «الرفض فقط», busy mode or «إيقاف 30 د»), both with operations' required note (`rejectBody` builds the body, `useDecideOnBehalf` sends it). A refusal says the order moved on (`order_state_changed`) or the choices changed. A rejected order's detail shows its label, the items, what the customer sees and whether operations rejected it.
- **«إلغاء الطلب» (AP §9.3.2, docs/domain/09, slice 2.8c):** while the detail carries `cancelChoices` (placed, accepted, ready), a session holding `operations.manage` (`canCancel`) gets the dialog: a reason of Content's `ops_cancel` list, the responsible party (AP Appendix C), «تم تحضير الطعام؟» from acceptance on, «تعويض الكابتن» while the preview allows it, the cash question with what the captain paid while the preview asks it, and operations' required note. The preview (`cancelPreviewQuery`) is asked again on each choice once a party is chosen and on each new version of the order (its key holds the detail's `version`, so the confirm never follows entries the operator did not see), keeping the previous answer while the next loads with the confirm off; `previewLines` turns its entries into one sentence per journal in docs/domain/09's style (owner decision 2026-11-10), leaving out `platform.order_clearing`, plus the strike; an entry whose sign is not the sentence's, a journal posting an account twice or a type it cannot name is `unknown` and blocks the confirm. «تعويض الكابتن» stays shown while ticked, so a `captain_pay_unset` refusal can be undone. `cancelBody` drops what the preview no longer allows; `useCancelOrder` keeps one key per choice. A cancelled order's detail shows the label, who, the note (operations' or the customer's «سبب آخر» text), what the customer sees, the party, the food, the cash answer, the credit, the compensation and both acknowledgements; its timeline line adds the label and the party.
- **«سحب وإعادة تعيين» (AP §9.3.2, AP §8.1, slice 2.12a):** while the detail carries `reassignChoices` (accepted or ready with a captain: Content's reassignment reasons with their default fault), a session holding `operations.manage` (`canReassign`) gets `ReassignOrder`: a reason, which prefills «بخطأ من الكابتن» or «دون خطأ» (`chooseReason`; owner decision 2026-11-10), the cash question with what the captain paid while the preview asks it, the preview (`reassignPreviewQuery`, asked on opening and on each answer, keyed by the detail's `version`; its lines are the cancellation's `previewLines` and `PreviewSentence`, «لا قيود مالية لهذا السحب.» when empty, an `unknown` line blocking the confirm), «بعد السحب» («إعادة الطلب للتوزيع» or «اختيار كابتن آخر الآن», which opens the picker once the withdrawal is done), and operations' required note; `reassignBody` drops a cash answer the preview no longer asks, `useReassignOrder` keeps one key per choice, and `pickup_request_open` says to wait for the restaurant. The detail lists every withdrawal under the captain («سحب الطلب من الكباتن»: the time, the captain's name, the label, the fault, the cash answer and the note), and the timeline names `order.reassigned`.
- **«تسليم لكابتن آخر» (AP §9.3.2, CA §9.10.1, slice 2.12b):** while the detail's `handover.allowed` (picked up or arrived with a captain, no handover open, no outcome waiting), a session holding `operations.manage` (`canHandOver`) gets the link to `/orders/$orderId/handover` (`OrderHandoverPage`, beside the picker): operations' required note first (`handoverNote`), then the picker, which after the pickup the server measures from the order's captain and leaves them out («{المسافة} عن الكابتن الحالي»), each eligible captain with «تسليم إلى {الاسم}»; `useHandOver` keeps one key per captain and note, and answers the offer «استلام من كابتن» with its seconds or the assignment. The reasons a captain is greyed out are `ineligibleKeys` in `assign-captain.ts`, shared by both pickers. The detail lists every handover under the captain («التسليم لكابتن آخر»: the time, both captains, `handoverState`: waiting for the offer's answer, waiting for the receipt, received at, or closed with `handoverCloseKeys`, and the note), and the timeline names `order.handover_offered`, `order.handover_assigned`, `order.handover_closed` and `order.handed_over`.
- **«أقصى مبلغ أحمله» in the picker (C4, K2, CA §8.4, slice 2.15a):** a captain greyed out only for `above_max_pickup` («المبلغ أكبر مما يحمله») keeps a button, «إرسال عرض إلى {الاسم} رغم ذلك», with the note that the captain sees the warning and decides (`canOffer`, the picker's `offerable`), only while the picker's `assignsAsOffer` says «تعيين» arrives as an offer: the server refuses it as a direct assignment.
- **«تحرير الجهاز» (AP §9.7.5, CA §4.9, slice 2.12c; owner decision 2026-11-11: on the order detail until AP §9.7's captain page):** on an active order with a captain (accepted to arrived), a session holding `captains.manage` (OWN, OPS; `canReleaseDevice`) gets `ReleaseDevice` under the captain line: the phone signed in and since when (`captainDeviceQuery`), a required reason (`releaseReason`) and «تحرير الجهاز», which signs that phone out (its `sessionId`) so the captain signs in on another one and continues the order; `useReleaseDevice` sends no key and reads the device again after each answer (`releaseResult`: a release of a phone no longer signed in answers `no_device`, «لا يوجد جهاز مسجّل دخوله لهذا الكابتن.»).
- **«فصل من الاتصال» (AP §9.7.5, CA §7.6, K18, slice 2.13a):** beside «تحرير الجهاز» on the same condition (`canReleaseDevice`), `ForceOffline` shows the captain's state (`captainAvailabilityQuery`) and, while the captain is online and not already forced (`canForceOffline`), a required reason the captain sees and «فصل من الاتصال»; `useForceOffline` sends no key and reads the state again; the answer says whether the captain is offline now or after this order.
- **The customer not answering (CA §9.9, AP §9.1.3, slice 2.13d; owner decisions 2026-11-11):** the detail's `NoAnswerSection` (`order-no-answer-page.tsx`) lists the captain's pings with the customer's answer («أنا قادم» or «سأتصل بالمستلم», `pingAnswerKeys`) and each «الزبون لا يستجيب» with operations' «انتظر» and its message, nothing before the first ping. While `noAnswer.waitAllowed` a session holding `operations.manage` (`canWaitForCustomer`) gets `WaitForCustomer`: the required message to the captain (up to 300 characters, `waitBody`) and «إرسال «انتظر»» (`useWaitForCustomer`, one key per message; `order_state_changed` says nothing waits any more); the same form sits on the alert «زبون لا يرد» in `/alerts` (`WaitOnAlert`), beside «فتح الطلب», whose «تحديد النتيجة» ends a fake or failed order. The timeline names the four door events.
- **«تعديل الوقت» and the item report (AP §9.3.2, RA §8.12, slice 2.9):** while the detail carries `timeChange` (accepted, ready, picked up), a session holding `operations.manage` (`canChangeTime`) gets «تعديل الوقت»: +5, +10, +15, +20 (`timeChips`, within the ceiling) or any whole minute from 1 to `maxMin` (`addMinFits`), the optional note, whether the prep time moves too (`prepMoves`: only while accepted), and the promised time now and after the change, rounded up to the next 5 minutes as the server does (`newPromisedAt`); `useChangeTime` keeps one key per choice. While `itemReport` is open every reader sees «صنف نفد بعد القبول» with the items, each «حتى الغد» or «حتى أعيده», the restaurant's note (a reason of Content's `item_unavailable_note` list, shown by its label as given) and the time, and `operations.manage` (`canCloseItemReport`) gets «إغلاق بلاغ صنف نفد» with the required reason (`useCloseItemReport`). The timeline names `order.time_changed` (with the event's `timeChange`: «+{د} د» and the new promised time on the city's clock), `order.item_reported` (with the event's `itemReport`: the items and the note's label), `order.item_report_withdrawn` and `order.item_report_closed`, with operations' own text as written.
- **«تعديل الطلب» (AP §9.3.3, slice 2.10a):** while the detail carries `editChoices` (placed, accepted, ready: the extra prep time's maximum and the menu's orderable items with their available options), a session holding `operations.manage` (`canEdit`) gets the dialog: each current line's quantity by its `position` (0 removes it; a line whose options change is removed and added again, owner decision 2026-11-10), lines added from the menu with options within each group's limits (`optionsFit`), a new delivery fee typed in major units (`minorOf` in `format.ts`; empty keeps it), the extra prep time when items are added to a ready order (`needsExtraPrep`), and operations' required note. `editRequest` builds the body, null until something changes and everything fits; the preview (`editPreviewQuery`, keyed by the detail's `version` as the cancel preview) shows the changes and the items value, fee, total, commission and merchant net before and after, whether the restaurant must acknowledge and the new promised time; the confirm waits for a fresh preview; `useEditOrder` keeps one key per choice. The form starts again whenever the order's lines change (`editKey`). The detail marks lines «أُضيف» and their earlier quantity, lists removed lines struck through, and lists every edit with its money, extra prep time, changes and the restaurant's acknowledgement; the timeline names `order.edited` and `order.edit_acknowledged`, and the alert `edit_unacknowledged` is «المطعم لم يؤكد التعديل». After the pickup (slice 2.10b, `editChoices.afterPickup`: picked up or arrived, no menu) the dialog offers only lower quantities and a lower fee (`editRequest` with the current fee refuses the rest), «المسؤول عن التعديل» («المطعم», «الكابتن», «المنصة»), and below the money the entries as `afterPickupLines` names them in «إلغاء الطلب»'s style (a debit on the restaurant, the reversed commission, the captain's charge, the platform's operating cost; anything else is `unknown` and blocks the confirm) with «المبلغ الجديد للتحصيل»; the confirm waits for the party. Such an edit in the detail shows its party and what it bore instead of the acknowledgement.
- **«تحديد النتيجة» (AP §9.3.2, §8.9, docs/domain/09, slice 2.11a):** while the detail carries `outcomeChoices` (picked up or arrived: Content's `food_after_failed` foods), a session holding `operations.manage` (`canSetOutcome`) gets the dialog: the outcome (AP Appendix C), «سُلّم الطلب للزبون رغم التلف» for a damaged one, the responsible party (`partiesFor`: the customer for a fake order only, set by itself), where a failed order's food went (`foodsFor`: «أُعيد إلى المطعم» only with the restaurant responsible), on a delivered order the amount still to collect typed in major units (`amountToCollectOf`, empty is 0; the server keeps it below the order total, slice 2.11b), «لا يُحصَّل شيء من الزبون.» or, when the preview is `provisional`, that the order waits «بانتظار تسجيل التحصيل» with provisional entries, and operations' required note. The preview (`outcomePreviewQuery`, keyed by the detail's `version` as the cancel preview) is asked once an outcome and a fitting party are chosen; `outcomeLines` turns it into docs/domain/09's sentences: first what the captain collects (the preview's `custody.collect`) and what that leaves against the pickup payment (the desk pays the captain back the rest, or the captain hands in what is beyond it), then one per journal (the commission, the restaurant's «استرداد مبلغ الاستلام», the customer's dues and block, the captain's pay by its counter, the captain's charge with its reason, a charge given back, the platform's cost or one given back, what was collected lowering the pay's cost (the journal's reason «ما دفعه الزبون يغطّي أجر الكابتن»), the delivery revenue beyond the costs), leaving out the order clearing account and the commission's revenue side; anything else is `unknown` and blocks the confirm. `useSetOutcome` keeps one key per choice. The detail then shows the outcome, the party, the time, the food, the loss, the dues, what the restaurant returns, the captain's pay, what the customer sees and the note; the timeline names `order.outcome_set` with the outcome's label and `order.outcome_collected`. While `outcome.awaitingCollection` (K9) the board's card has «بانتظار تسجيل التحصيل», the detail says so with the amount, and `operations.manage` (`canRecordOutcomePayment`) gets «تسجيل التحصيل نيابة عن الكابتن» (`RecordOutcomePayment`): what was received and given back in the base currency only (the captain's screen takes the other currencies), the shortfall's reason from Content's `shortfall` list once the server answers `shortfall_reason_required`, and the required reason; `useRecordOutcomePayment` keeps one key per body.
- **«تغيير النتيجة» (AP §8.9, §9.3.2, slice 2.11c):** while the detail carries `outcomeChange` (a finished order within `order.outcome_change_days` of its first outcome: `until` and the foods), a session holding `orders.change_outcome` (OWN, `canChangeOutcome`) gets `ChangeOutcome`, the outcome dialog started from the outcome in force (`changeFormOf`) with no amount: an amount collected stays, so only «مجاني» and a delivered «تالف» are offered then (`outcomesFor`). `changePreviewBody` is null until something differs from the outcome in force; the preview (`outcomeChangePreviewQuery`, keyed by the detail's `version`) shows what the change undoes, the `reversed` entries signed back and named by the outcome's own sentences, then what it posts (`changeLines`, both through `journalLines` from `order-outcome.ts`; an `unknown` sentence blocks the confirm), and the confirm needs the required reason (`useChangeOutcome`, one key per choice; `outcome_change_closed` says the days passed). The dialog starts again on each new version of the order. The detail's outcome lists the outcomes replaced («النتائج السابقة», `outcome.history`), and the timeline names `order.outcome_changed`.
- **Commands (architecture §5.3):** a command that takes `Idempotency-Key` keeps one key per choice until an answer arrives (`useAssignCaptain`), so a retry after a lost answer replays instead of acting twice.
- **Content-Security-Policy (`infra/nginx/headers.conf`):** `default-src 'self'` (and `connect-src 'self' wss://<host>` for the WebSocket) on staging and production, so no inline script or style, no `data:` image and no third-party origin. Draw generated images as inline SVG (the setup page's QR code). The Playwright tests run without it, so check a new kind of resource against it.
- **Types:** `tsconfig.json` types `src` for the browser (DOM and `vite/client`, no Node globals); `tsconfig.node.json` types `e2e`, `test` and the config files for Node.
- **Design stop:** no styling, design tokens or shared UI package until the owner says the UI/UX and the design system are ready (root `CLAUDE.md`). Layout, when it comes, uses start and end, never left and right.
- **Smoke test:** `e2e/` runs the built app (`vite preview`) in Chromium and answers its API calls with `page.route`, so it needs no server. Each app previews on its own port (admin 4173, portal 4174) because Turborepo runs them together.

## Commands

From the repository root, after `docker compose up --detach` and the server on port 3000:

- `pnpm --filter @fox-drop/admin dev`: the panel on http://localhost:5173 (the portal: `@fox-drop/merchant-portal`, port 5174).
- `pnpm --filter @fox-drop/admin test:e2e`: build first (`build`), then the smoke test. `pnpm verify` runs both for every app and installs Chromium once.
